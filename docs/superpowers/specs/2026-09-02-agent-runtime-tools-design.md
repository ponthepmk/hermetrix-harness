# Agent runtime tools — design

วันที่ตกลง: 2026-09-02
สถานะ: spec รอ implement
ขอบเขต: spec ที่ 2.5 จาก 7 · spec 1 ลงแล้ว · spec 2 (Code view) เขียนแล้วรอคิว

## 1. ปัญหา

Direct tool waist ทั้ง 11 ตัวคือ `context_search`, `skill_search`, `skill_view`,
`skill_manage`, `tool_call`, `tool_describe`, `tool_search` และ `workspace.*` สี่ตัว

ไม่มี terminal ไม่มี browser ไม่มี command แม้ทั้งสองอย่างจะมีจริงและทำงานได้
`grep browser internal/tools/registry.go` ไม่เจออะไรเลย ขับได้จาก UI เท่านั้น

แปลว่า agent **อ่านและเขียนไฟล์ได้ แต่รันเทสต์ไม่ได้และดูหน้าเว็บไม่ได้**
agent ที่แก้โค้ดแล้วตรวจงานตัวเองไม่ได้ ไม่ใช่เครื่องมือเขียนโค้ด และ QC กับ load test
ใน spec 3.5 ต่อยอดจากช่องว่างนี้ไม่ได้เลย

## 2. เครื่องมือใหม่สองตัว ไม่ใช่แปด

waist โตจาก 11 เป็น **13** เจ้าของรับราคานี้แล้ว ทั้งคู่เป็น action-based

```
workspace.run   action: start | status | cancel
browser         action: open | navigate | back | read | click | type | capture | close
```

เหตุผลที่ไม่แยกเป็นตัวๆ: แปด schema อยู่ในทุก request ตลอดไปเพื่อความสามารถที่ใช้เป็นครั้งคราว
เหตุผลที่ไม่ยัดลง deferred catalog แบบ MCP: `go test` ไม่ใช่ความสามารถหายาก มันคือสิ่งที่
agent ใช้ทุกครั้งที่แก้โค้ด การให้มันค้นหาก่อนใช้ทุกครั้งคือจ่ายสาม round-trip เพื่อ
ประหยัดสอง schema

## 3. Job runner ไม่ใช่ PTY

ทั้งสองมีอยู่แล้วและต่างกันมาก

| | Job runner (`StartCommand`) | PTY (`StartTerminal`) |
|---|---|---|
| รูปแบบ | one-shot มีจุดจบ | interactive มีสถานะ |
| ขอบเขต | allowlist, dir ผูก root, env ไม่มี secret, timeout, เพดาน output, kill ทั้ง process group | shell เต็ม พิมพ์อะไรก็ได้ |
| หลักฐาน | receipt artifact ที่ลบไม่ได้ | output tail |

**agent ได้ job runner** เพราะ `go test` มีจุดจบ ตรวจสอบได้ และทิ้งใบเสร็จ
agent ที่ขับ shell แบบ interactive คุมขอบเขตยากกว่ามากและ reproduce ไม่ได้

PTY ยังเป็นของผู้ใช้เหมือนเดิม agent ไม่ได้

## 4. Async ที่ไม่เผา turn

`go test ./...` ในรีโปนี้ใช้เวลาราว 40 วินาที เพดานเดิมของ job runner คือ 120 วินาที
ซึ่งไม่พอสำหรับ build ใหญ่ เจ้าของเลือก async

ปัญหาตรงๆ ของ async คือ agent จะ poll รัวๆ แล้วเผา turn ทิ้ง

**`status` เป็น long-poll** บล็อกรอได้ถึง 30 วินาทีต่อครั้งก่อนตอบ ไม่ใช่ตอบทันทีว่า
ยังไม่เสร็จ งาน 40 วินาทีจึงเป็น `start` บวก `status` สองครั้ง ไม่ใช่ยี่สิบครั้ง

**เพดานแข็ง 10 นาทีต่อ job** agent ไม่ถูกบล็อกก็จริง แต่ process ที่หลุดต้องตาย
`cancel` ใช้กลไก kill ทั้ง process group ที่มีอยู่แล้ว

**สอง job พร้อมกันต่อ session** เกินกว่านั้นถูกปฏิเสธพร้อมบอกว่ามีอะไรค้างอยู่
สองพอสำหรับรูปแบบที่เกิดจริง คือรันเทสต์ค้างไว้แล้วรัน `git diff` ดูระหว่างรอ
และมันเป็นเพดานที่ทดสอบได้ ไม่ใช่การเดาว่าเครื่องรับไหวเท่าไหร่ agent ที่วนลูป
จึงติดที่สองงาน ไม่ใช่จุดไฟทั้งเครื่อง

## 4.5 รากเดียวต่อ session ไม่ใช่รากเดียวต่อโปรเซส

`toolruntime.NewRegistry(*workspace)` ที่ `cmd/hermetrix/main.go:204` ตั้ง root ครั้งเดียว
ตอน start และ `workspace.list_files`, `read_file`, `search_files`, `write_file` ทุกตัว
ใช้ `r.root` นั้นเสมอ ไม่ได้ดูว่า session ผูกกับโปรเจคไหน

เดิมไม่เจ็บเพราะ `EnsureWorkspaceProject` ลงทะเบียน `--workspace` เป็นโปรเจคและ pin ไว้
session ส่วนใหญ่จึงบังเอิญตรงกัน **spec 1 ทำให้ picker เป็นประตูหน้า** การเปิดโปรเจคอื่น
กลายเป็นเรื่องปกติ และตั้งแต่นั้นการเปิดโปรเจค B แล้วให้ agent อ่านไฟล์ จะอ่านจากรากของ
โปรเจค A

สเปคนี้ชนกับข้อนั้นโดยตรง หัวข้อ 5.1 บอกว่า working directory ผูกกับ project root
ถ้าทำตามนั้นโดยไม่แก้อะไร `workspace.run` จะรันในรากหนึ่งขณะที่ `workspace.read_file`
อ่านจากอีกราก **ใน session เดียวกัน** agent จะแก้ไฟล์ที่หนึ่งแล้วรันเทสต์อีกที่หนึ่ง

**ตัดสิน: สเปคนี้แก้รากของ `workspace.*` ทั้งหมดให้เป็นของ session**

- root ของ `workspace.*` ถูกกำหนดตอนเรียก ไม่ใช่ตอนสร้าง registry ผู้เรียกขอ registry
  ที่ผูกกับ root ของ session ก่อนแล้วจึง execute
- ผู้เรียกคือ agent service ซึ่งมี `session` อยู่ในมือแล้ว จึง resolve จาก
  `session.Contract.ProjectID`
- โปรเจคที่ไม่มีโฟลเดอร์โค้ด ทำให้ `workspace.*` ปฏิเสธด้วยเหตุผลเดียวกับที่ spec 1
  กำหนดไว้ ไม่ใช่ fallback ไปที่รากอื่น session ที่เปิดใน Inbox จึงอ่านไฟล์ไม่ได้
  ซึ่งถูกต้อง เพราะ Inbox ไม่มีโฟลเดอร์โค้ด

`--workspace` ยังทำงานเหมือนเดิมในฐานะโปรเจคที่ลงทะเบียนและ pin ตอน start
สิ่งที่เปลี่ยนคือมันไม่ใช่รากลับที่ทุก session ใช้ร่วมกันอีกต่อไป

### 4.6 agent ไม่รู้จัก product

`grep -rn "product\." internal/agent` ไม่คืนอะไร แพ็กเกจ agent ไม่ import product เลย
tool ใหม่ทั้งสองต้องผ่าน interface ที่ประกาศฝั่งผู้เรียก และ `product.Service` เป็นผู้
implement โดย `cmd/hermetrix/main.go` เป็นที่ประกอบ

นี่คือ pattern เดียวกับ `mcp.ServerRequestHandler` ที่ใช้อยู่แล้วสำหรับ sampling และ
elicitation ไม่ใช่โครงสร้างใหม่

## 5. Authority

ตกลงไว้แล้วใน spec 1 §9.3 คัดมาที่นี่เพื่อไม่ให้ถูกตัดสินใหม่ตอนเขียนโค้ด

### 5.1 รันคำสั่ง: allowlist เดิม ไม่ต้องขออนุมัติรายครั้ง

allowlist คือชุดเดียวกับที่ `internal/product/commands.go` ใช้อยู่:
`go`, `git`, `node`, `npm`, `python3`, `rg`, `ls`

เหตุผลที่ไม่ขอ: agent ที่ต้องขออนุญาตทุกครั้งที่จะรันเทสต์ จะไม่รันเทสต์ ซึ่งทำให้มันกลับไป
เป็น agent ที่ตรวจงานตัวเองไม่ได้เหมือนเดิม สิ่งที่ทำให้ปลอดภัยคือ**ขอบเขต** ไม่ใช่การถาม:
executable ที่ระบุชื่อได้ · working directory ผูกกับ project root · environment จำกัด
ไม่มี secret · deadline · เพดาน output · ยกเลิกได้ทั้ง process group · receipt เป็น
artifact ที่ลบไม่ได้

**working directory ที่ agent ระบุได้ต้องผ่าน `resolveInside` เดียวกับที่ไฟล์ใช้**
`CommandInput` มีฟิลด์ `WorkingDir` และถ้า agent ส่ง `../..` มาโดยไม่มีการตรวจ
ขอบเขตที่เหลือทั้งหมดก็ไม่มีความหมาย ค่าว่างหมายถึง project root

**ข้อจำกัดที่ต้องเขียนไว้ตรงๆ: นี่คือ process hardening ไม่ใช่ OS sandbox**
คำสั่งใน allowlist ยังรันโค้ดที่อยู่ใน repo ได้ `go test` รันเทสต์ที่ repo นั้นเขียนไว้
ถ้าจะเปิด repo ที่ไม่ไว้ใจ ต้องรันทั้ง Hermetrix ใน container

### 5.2 Browser: loopback เลย ภายนอกขออนุมัติ

ตรวจ UI ที่ตัวเองเพิ่งแก้คือเหตุผลหลักที่ agent ต้องมี browser และมันอยู่บน localhost เสมอ
เน็ตข้างนอกเป็นคนละเรื่อง ใช้กลไก approval ที่มีอยู่แล้ว

### 5.3 เนื้อหาหน้าเว็บเป็น untrusted evidence เสมอ

ไม่ว่ามาจาก loopback หรือข้างนอก กฎนี้มีอยู่แล้วใน managed browser ปัจจุบัน
(DOM snapshot ถูกติดป้าย) และต้องคงไว้: ข้อความบนหน้าเว็บที่สั่งให้ agent ทำอะไร
คือข้อมูล ไม่ใช่คำสั่ง

ข้อนี้สำคัญขึ้นเมื่อ agent เป็นคนขับเอง เพราะ agent เป็นผู้อ่านคนแรก ไม่ใช่ผู้ใช้

## 6. Learning: ใบเสร็จการรันคือหลักฐาน ไม่ใช่ของประดับ

นี่คือส่วนที่ทำให้ spec นี้มีค่ามากกว่าการเพิ่ม tool สองตัว

`learning.Digest` มี `Outcome string` และ `ToolReceipts []string` อยู่แล้ว แต่วันนี้
`Outcome` เป็น**ข้อความที่บรรยาย** ไม่ใช่สิ่งที่พิสูจน์แล้ว ไม่มีอะไรในระบบแยกได้ว่า
"งานสำเร็จ" มาจากการวัดหรือมาจากความรู้สึก

spec 1 เปลี่ยน default ให้ agent promote Skill ที่มันเขียนเองได้โดยไม่ต้องรออนุมัติ
การ auto-promote Skill ที่มาจาก turn ซึ่งไม่มีใครพิสูจน์อะไรเลย คือความเสี่ยงที่การเปลี่ยน
นั้นสร้างขึ้น สเปคนี้ปิดมัน

### 6.1 สิ่งที่ต้องทำ

- ใบเสร็จของทุก `workspace.run` เข้าไปใน `Digest.ToolReceipts` พร้อม executable,
  argument, exit status และเวลาที่ใช้
- `Digest` ได้ฟิลด์ที่แยก **outcome ที่วัดแล้ว** ออกจาก **outcome ที่อ้าง** ค่าที่วัดแล้ว
  ต้องอ้างอิงใบเสร็จจริงได้ ไม่ใช่ boolean ที่ใครก็ตั้งได้
- reviewer ใช้ความต่างนั้น: turn ที่มีคำสั่งซึ่งล้มเหลวก่อนแล้วผ่านหลังการแก้ เป็นหลักฐาน
  คนละชั้นกับ turn ที่ไม่มีการรันอะไรเลย
- Skill ที่ถูกเสนอจาก turn ที่ไม่มีการพิสูจน์ **ต้องบอกว่าไม่มี** ในเหตุผลของมัน
  ผู้ใช้ที่เปิด Skill Studio ต้องเห็นความต่างนี้ได้โดยไม่ต้องขุด

### 6.2 สิ่งที่ยังไม่ทำในสเปคนี้

ไม่เปลี่ยนกฎ authority ให้ผูกกับการพิสูจน์ นั่นเป็นการเปลี่ยน policy อีกครั้งและควรทำเมื่อ
มีข้อมูลจริงว่าสัดส่วน turn ที่พิสูจน์แล้วเป็นเท่าไหร่ สเปคนี้ทำให้ข้อมูลนั้น**มีอยู่**
การตัดสินใจใช้มันเป็นเรื่องถัดไป

## 7. Error handling

แต่ละอย่างมีข้อความของตัวเองที่บอกสาเหตุจริง

| สถานการณ์ | agent เห็น |
|---|---|
| โปรเจคไม่มีโฟลเดอร์โค้ด | `ErrProjectHasNoCode` พร้อมบอกว่าตั้งได้ที่ไหน |
| executable นอก allowlist | บอกว่าอนุญาตอะไรบ้าง ไม่ใช่ "ไม่อนุญาต" ลอยๆ |
| เกินเพดาน 10 นาที | บอกว่ารันไปกี่วินาทีและถูกยกเลิกแล้ว ไม่ใช่ "failed" |
| output เกินเพดาน | ตัดพร้อมบอกขนาดจริง |
| `status` กับ job ที่ไม่มี | บอกว่าไม่มี job นี้ ไม่ใช่คืนสถานะว่าง |
| browser ออกเน็ตโดยไม่อนุมัติ | บอกว่าต้องอนุมัติและอนุมัติที่ไหน |
| job เกินจำนวนพร้อมกัน | บอกว่ามีกี่ job ค้างอยู่ |

## 8. Testing

- `start`, `status`, `cancel` กับคำสั่งจริงที่รู้ผลล่วงหน้า ทั้งที่สำเร็จและที่ exit ไม่เป็นศูนย์
- `status` แบบ long-poll คืนภายในเพดานเวลา ไม่ค้างและไม่ตอบทันทีว่ายังไม่เสร็จ
- เพดาน 10 นาทีฆ่า process จริง ทดสอบด้วยคำสั่งที่จงใจไม่จบ
- executable นอก allowlist ถูกปฏิเสธ และ argument ที่มี `;` หรือ `|` ไม่ทำให้เกิด shell
  เพราะไม่มี shell ให้เกิด
- โปรเจคไม่มี root ถูกปฏิเสธด้วย `ErrProjectHasNoCode` ทั้ง `workspace.run` และ
  `workspace.*` ที่อ่านเขียนไฟล์
- session ที่ผูกกับโปรเจค B อ่านไฟล์ของโปรเจค B ไม่ใช่ของ `--workspace` เทสต์นี้จับ
  พฤติกรรมเดิมโดยตรง

**เพดานเวลาของคำสั่ง** `StartCommand` เดิมบังคับ `timeout_seconds` อยู่ในช่วง 1 ถึง 120
สเปคนี้เลือก 10 นาที ตอนที่เขียนยังไม่รู้ว่ามีเพดาน 120 วินาทีอยู่ ตัดสินตามสเปค คือ
ขยายเพดานเป็น 600 วินาที เพราะ `go build` หรือชุดเทสต์เต็มของโปรเจคจริงเกิน 120 วินาทีได้
ค่า default ยังเป็น 30 วินาทีเหมือนเดิม UI ไม่เปลี่ยนพฤติกรรม
- `working_dir` ที่พยายามหนีออกนอก root ถูกปฏิเสธ ทดสอบด้วย `../`, absolute path
  และ symlink ที่ชี้ออกนอก
- job ที่สามในหนึ่ง session ถูกปฏิเสธพร้อมบอกว่ามีอะไรค้าง
- browser: loopback ผ่านโดยไม่ขอ · URL ภายนอกถูกกักรออนุมัติ · เนื้อหาที่คืนมาติดป้าย
  untrusted
- waist มี 13 ตัวพอดี เทสต์ที่นับ waist ต้องระบุรายชื่อ ไม่ใช่แค่จำนวน
- digest ของ turn ที่รันคำสั่งมีใบเสร็จนั้นอยู่จริง และ turn ที่ไม่ได้รันอะไรแยกออกจากกันได้

## 9. นอกขอบเขต

PTY ให้ agent · การรัน git ที่เขียน (commit, checkout, stage) · การเพิ่ม executable
เข้า allowlist จาก UI · QC และ load testing ซึ่งเป็น spec 3.5 และต่อยอดจากสเปคนี้
