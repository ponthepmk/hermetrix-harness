# Code view — design

วันที่ตกลง: 2026-09-02
สถานะ: spec รอ implement
ขอบเขต: spec ที่ 2 จาก 7 · spec 1 (Shell + Project) ลงแล้ว

## 1. ปัญหา

Code view เป็นหนึ่งในสี่มุมมองของ shell และตอนนี้แสดงข้อความว่ายังไม่ได้สร้าง
สิ่งที่มันต้องทำคือสิ่งที่เจ้าของบอกไว้ตรงๆ: **อ่านและตรวจสิ่งที่ agent แก้เป็นหลัก**
แก้เล็กน้อยได้ ไม่ต้องการ autocomplete หรือ LSP

คำตอบนั้นตัดทางเลือกใหญ่ทิ้งไปหนึ่งทาง ดูหัวข้อ 2

### 1.1 diff ที่มีอยู่ไม่ใช่ diff

`boundedTextDiff` ที่ `internal/product/workbench.go:167` สร้างสิ่งที่เรียกตัวเองว่า
unified diff ด้วยวิธีนี้:

```go
minus := strings.ReplaceAll(clip(before), "\n", "\n-")
plus  := strings.ReplaceAll(clip(after),  "\n", "\n+")
```

มันเติม `-` หน้าทุกบรรทัดของไฟล์เดิม และ `+` หน้าทุกบรรทัดของไฟล์ใหม่ ไฟล์ 2,000 บรรทัด
ที่แก้บรรทัดเดียวจึงได้ผลลัพธ์ 4,000 บรรทัดที่ไม่มีใครอ่านได้ มันเป็น**ใบเสร็จว่ามีการ
เปลี่ยนแปลง** ไม่ใช่ diff และชื่อของมันบอกไม่ตรงกับสิ่งที่มันเป็น

จอ review พึ่งสิ่งนี้โดยตรง สเปคนี้จึงรวมการเปลี่ยนมันให้เป็น line diff จริงไว้ด้วย

## 2. สิ่งที่ตัดสินแล้ว

**ไม่ใช้ CodeMirror หรือ Monaco** server ส่ง
`Content-Security-Policy: default-src 'self'; style-src 'self'; script-src 'self'; …`
โดยไม่มี `'unsafe-inline'` ทั้งสองตัวฉีด `<style>` ตอน runtime (CodeMirror ผ่าน
`style-mod`) ซึ่งถูกบล็อก การใช้มันจึงต้องผ่อน CSP ที่ `ui_contract_test.go` เขียนเทสต์
คุ้มครองไว้เพราะเคยมีบั๊กจริงจากข้อนี้ บวกกับ build step ครั้งแรกของโปรเจค
(UI ตอนนี้คือ vanilla JS 4,178 บรรทัด ไม่มี bundler)

เมื่อเป้าหมายคืออ่านและตรวจ ราคานั้นแพงเกินสิ่งที่ได้ **เขียน renderer เอง**

**ทางเลือกที่ปฏิเสธ:** ไม่แตะ git แล้วอ่านจาก Hermetrix เองอย่างเดียว ไม่ต้องเพิ่ม
endpoint แต่จะเห็นเฉพาะสิ่งที่ผ่านเครื่องมือของ Hermetrix สิ่งที่ผู้ใช้แก้เองในเครื่อง
หรือที่ `go fmt` เปลี่ยนจะหายไป และเมื่อ spec 2.5 ให้ agent รันคำสั่งได้ ช่องว่างนั้น
จะกว้างขึ้นไม่ใช่แคบลง

## 3. แหล่งข้อมูลสองชั้น

git กับ transcript ตอบคนละคำถาม และจอเดียวที่มีทั้งคู่คือสิ่งที่ IDE ทั่วไปให้ไม่ได้

| ชั้น | ตอบว่า | มาจาก |
|---|---|---|
| git | ตอนนี้ต่างจาก HEAD ยังไง รวมสิ่งที่แก้นอก Hermetrix | endpoint ใหม่ |
| transcript | ใครแก้ ตอนไหน turn ไหน ภายใต้ approval ไหน | `agent_events` ที่มีอยู่แล้ว |

### 3.1 ที่มาของการแก้ไฟล์อยู่ใน transcript ไม่ใช่ artifact

ร่างแรกของสเปคนี้บอกว่าให้อ่าน artifact `workbench_diff` เป็นชั้นที่สอง **นั่นผิด**
`grep -c CreateArtifact internal/tools/registry.go` คืน 0: `workspace.write_file`
ของ agent เขียนไฟล์แบบ atomic แล้วบันทึก `previous_sha256` กับ `sha256` ลงใน metadata
ของ tool receipt เท่านั้น มันไม่สร้าง artifact ใดๆ

artifact `workbench_diff` มาจาก `product.WriteProjectFile` ซึ่งเป็นเส้นทางของ
**file editor ฝั่ง UI** คนละเส้นกับที่ agent ใช้ ใครที่อ่านแต่ artifact จะเห็นเฉพาะ
สิ่งที่ตัวเองพิมพ์ ไม่เห็นสิ่งที่ agent ทำเลย ซึ่งตรงข้ามกับจุดประสงค์ของจอนี้

ที่มาที่แท้จริงของการแก้ไฟล์โดย agent คือ session transcript: `tool_call` และ
`tool_result` ที่มี `tool_name = workspace.write_file` พร้อม path, `previous_sha256`,
`sha256` และ `step_binding_id` และคู่กับ `approval_required` / `approval_decision`
ของการเขียนครั้งนั้น

**การจับคู่** git บอกว่าไฟล์ X เปลี่ยน transcript บอกว่า turn ไหนเขียน X ด้วย
before-SHA อะไร จับคู่กันด้วย path ซึ่งมีอยู่ใน argument ของ tool call

### 3.2 endpoint ใหม่

`GET /api/projects/{id}/changes` คืนสถานะไฟล์ที่เปลี่ยนและ diff ของแต่ละไฟล์

- รัน `git status --porcelain=v1` และ `git diff` ด้วยกลไก bounded เดียวกับ
  `internal/product/commands.go` ใช้อยู่: executable ที่ระบุชื่อได้ · working directory
  ผูกกับ project root · environment จำกัดไม่มี secret · deadline · เพดาน output
- **อ่านอย่างเดียว** ไม่มี subcommand ที่เขียน ไม่รับ argument จากผู้ใช้ ชื่อไฟล์ที่ส่ง
  ให้ git ต้องมาจากผลของ `git status` เอง ไม่ใช่จาก query string
- `RequireRoot` ก่อนเสมอ โปรเจคที่ไม่มีโฟลเดอร์โค้ดถูกปฏิเสธด้วยเหตุผลจริง

### 3.3 endpoint ที่สอง สำหรับที่มา

`GET /api/projects/{id}/file-history?path=...` คืนรายการครั้งที่ไฟล์นั้นถูกเขียน
จาก `agent_events` เรียงใหม่ไปเก่า แต่ละรายการมี session, turn, เวลา, before/after SHA
และ approval ที่อนุมัติมัน ถ้ามี

path ที่รับมาต้องผ่าน `resolveInside` เดียวกับที่ไฟล์อื่นใช้ ไม่ใช่เอาไปค้นดิบๆ

### 3.4 เมื่อไม่มี git

โปรเจคที่ไม่ใช่ git repo หรือเครื่องที่ไม่มี `git` ติดตั้ง ต้องบอกว่าอะไรขาด และ Code view
ยังใช้ดูไฟล์ แก้ไฟล์ และดูประวัติจาก transcript ได้ตามปกติ **หายไปเฉพาะรายการสิ่งที่
เปลี่ยนเทียบ HEAD ไม่ใช่ทั้งจอ**

## 4. Tokenizer

เขียนเอง คืน `<span class="tok-*">` และสีมาจาก stylesheet static ไม่มี inline style
จึงไม่แตะ CSP และไม่ต้องมี build step

รองรับภาษาที่รีโปนี้มีจริง: Go, JavaScript, CSS, HTML, Markdown, JSON, shell
นามสกุลที่ไม่รู้จักแสดงเป็น plain text **ไม่เดาแล้วทาสีมั่ว** เพราะ highlight ที่ผิด
อ่านยากกว่าไม่มี highlight

ข้อจำกัดที่ยอมรับล่วงหน้า: tokenizer เขียนเองจะพลาด edge case ที่ของสำเร็จจับได้
เช่น regex กับการหาร nested template literal และ heredoc ในเชลล์ เป้าหมายคืออ่านโค้ด
ของโปรเจคนี้ได้ ไม่ใช่ความถูกต้องระดับ compiler

**ทุก token ต้อง escape ก่อนใส่ DOM** ไฟล์ที่มี `<script>` อยู่ในเนื้อหาต้องแสดงเป็น
ข้อความ ไม่ใช่ทำงาน ข้อนี้มีเทสต์

## 5. Diff

### 5.1 แทน boundedTextDiff ด้วย line diff จริง

git ให้ diff ของสิ่งที่ต่างจาก HEAD อยู่แล้ว แต่ `boundedTextDiff` ยังถูกใช้ทุกครั้งที่
ผู้ใช้กด save ในตัวแก้ไฟล์ และผลของมันถูกเก็บเป็น artifact ถาวรที่อ่านไม่ได้ ของที่เรียก
ตัวเองว่า diff แต่ไม่ใช่ diff เป็นคำที่ไม่จริง และจอนี้จะแสดงมัน

ใช้ LCS/Myers ใน Go ผลลัพธ์ยังเป็น unified diff และยังเก็บเป็น artifact เดิม
แต่แสดงเฉพาะบรรทัดที่ต่างพร้อม context

รูปแบบ artifact เปลี่ยน ซึ่งเป็นการเปลี่ยนที่ตั้งใจ: artifact เดิมอ่านไม่ได้อยู่แล้ว
artifact เก่าที่สร้างไว้แล้วไม่ถูกแก้ย้อนหลัง เพราะ artifact เป็น immutable

### 5.2 การแสดงผล

unified view พร้อม hunk header และเลขบรรทัดทั้งสองฝั่ง แต่ละบรรทัดยัง highlight
ตามภาษาของไฟล์ diff ที่ยาวเกินเพดานถูกตัดพร้อมบอกว่าตัดไปกี่บรรทัด
**ไม่ใช่ตัดเงียบ**

## 5.3 ไฟล์ใหญ่: ตั้งเพดาน ไม่ใช่ virtualize

`maxWorkbenchFileBytes` คือ 2 MiB ซึ่งเป็นราว 40,000 ถึง 50,000 บรรทัด การ render
ทุกบรรทัดเป็นหลาย `<span>` พร้อมกันคือ DOM node หลักแสนตัวในครั้งเดียว และจะหน่วง
CodeMirror กับ Monaco แก้ข้อนี้ด้วย virtual scrolling ซึ่งเป็นเหตุผลหนึ่งที่คนใช้มัน

**ตัดสิน: ตั้งเพดานจำนวนบรรทัดที่ render แล้วบอกตรงๆ ว่าตัด** ไม่เขียน virtualization

เหตุผล จอนี้มีไว้อ่านและตรวจสิ่งที่เปลี่ยน ไม่ใช่ท่องไฟล์ generated ทั้งไฟล์ diff ที่ใหญ่
ถูกตัดอยู่แล้วตามหัวข้อ 5.2 และไฟล์ที่ใหญ่กว่าเพดานยังเปิดดูส่วนต้นได้ ยังแก้ได้ผ่านโหมด
แก้ไข และยังดูประวัติได้ครบ สิ่งที่หายคือการ scroll ผ่านบรรทัดที่ 30,000 ด้วยตา
ซึ่งไม่ใช่สิ่งที่คนทำกับไฟล์ขนาดนั้น

virtualization เป็นเครื่องยนต์ที่เราจะต้องดูแลเอง ตลอดไป และมันแก้ปัญหาที่จอนี้ยังไม่มี
ถ้าวันหนึ่งเปิดโปรเจคที่ต้องอ่านไฟล์ใหญ่จริงเป็นประจำ ข้อนี้ควรถูกทบทวน ไม่ใช่เพิ่มไว้ก่อน

ข้อความตอนตัดต้องบอกจำนวนบรรทัดจริงและจำนวนที่แสดง **หมวดที่ถูกตัดต้องรู้ว่าถูกตัด**

## 6. โครงจอ

โครงสามเขตจาก spec 1 ไม่เปลี่ยน Code view เติมเนื้อหาลงไป

| เขต | เนื้อหา |
|---|---|
| rail | file tree ของ project root และรายการไฟล์ที่เปลี่ยน พร้อม `+n −m` |
| main | pane ที่เลือกได้ระหว่าง Editor และ Diff ต่อ pane · เพิ่มสองรายการนี้เข้า `PANE_CONTENT` ที่ spec 1 สร้างไว้ (เดิมมี files, terminal, browser, output) |
| side | ที่มาของไฟล์ที่เลือก จาก `/file-history`: turn ไหน approval ไหน SHA อะไร |

ไฟล์ที่เปิดอยู่เป็น tab ในแต่ละ pane ปิดได้ และ pane หนึ่งเปิด Editor อีก pane เปิด Diff
ของไฟล์เดียวกันได้ นั่นคือเหตุผลที่ pane มีอยู่

## 7. การแก้ไฟล์ สองโหมด ไม่ใช่ overlay

อ่านคือ highlighted read-only กด Edit สลับเป็น `<textarea>` ธรรมดา Save ใช้
`PUT /api/projects/{id}/file` เดิมซึ่งมี `expected_sha256` อยู่แล้ว การชนกันจึงถูกจับได้
โดยไม่ต้องเพิ่มอะไร

**ไม่ทำ textarea โปร่งใสซ้อนบน highlight** ที่ต้อง sync scroll และ caret เป็นบั๊กคลาสสิก
และเราไม่ต้องการมัน เพราะจอนี้เน้นอ่าน การแก้เป็นทางออกฉุกเฉิน ไม่ใช่ทางหลัก

## 8. Error handling

แต่ละอย่างมีข้อความของตัวเองที่บอกสาเหตุจริง ไม่ใช่ "ไม่สามารถโหลดไฟล์"

| สถานการณ์ | ผู้ใช้เห็น |
|---|---|
| โปรเจคไม่มีโฟลเดอร์โค้ด | `ErrProjectHasNoCode` เดิม พร้อมบอกว่าตั้งได้ที่ไหน |
| ไม่ใช่ git repo | รายการสิ่งที่เปลี่ยนหายไป ไฟล์ยังเปิดได้ |
| ไม่มี `git` ติดตั้ง | เหมือนข้างบน แต่บอกว่าเป็นเรื่องของเครื่อง ไม่ใช่ของโปรเจค |
| ไฟล์ binary | บอกว่าเป็น binary และขนาดเท่าไหร่ ไม่พยายามแสดง |
| ไฟล์เกิน 2 MiB | เพดานเดิมของ workbench บอกขนาดจริง |
| Save ชน SHA | บอกว่าไฟล์ถูกแก้ระหว่างทาง ไม่เขียนทับ |

## 9. Testing

**Go**
- line diff ให้ผลถูกต้องกับกรณีที่รู้คำตอบล่วงหน้า: แทรกบรรทัดเดียว ลบบรรทัดเดียว
  แก้กลางไฟล์ ไฟล์ว่าง ไฟล์เหมือนกันทุกประการ
- diff ของไฟล์ใหญ่ที่แก้บรรทัดเดียวต้องสั้น ไม่ใช่ยาวเท่าไฟล์ นี่คือเทสต์ที่จับ
  พฤติกรรมเดิมโดยตรง
- `/changes` กับ git repo จริง กับไดเรกทอรีที่ไม่ใช่ repo และกับโปรเจคที่ไม่มี root
- คำสั่ง git ที่รันต้องไม่รับ argument จากผู้ใช้ เทสต์ยืนยันว่าไม่มีทางแทรกได้
- `/file-history` คืนรายการจาก `agent_events` จริง เรียงถูกทาง และ path ที่พยายาม
  หนีออกนอก root ถูกปฏิเสธ
- การจับคู่ git กับ transcript ด้วย path ให้ผลถูกต้องเมื่อมีไฟล์ชื่อซ้ำกันคนละไดเรกทอรี

**UI**
- tokenizer escape ทุก token: ไฟล์ที่มี `<script>alert(1)</script>` แสดงเป็นข้อความ
- diff ยาวถูกตัดพร้อมบอกจำนวน
- นามสกุลที่ไม่รู้จักได้ plain ไม่ใช่ token ผิดภาษา
- contract markers ตามกฎเดิมของไฟล์เทสต์นั้น

**เบราว์เซอร์จริง** เปิดไฟล์ อ่าน แก้ save · แก้ไฟล์จากที่อื่นแล้ว save ต้องถูกปฏิเสธ ·
โปรเจคที่ไม่ใช่ git repo ยังใช้งานได้ · ไม่มี horizontal overflow

## 10. นอกขอบเขต

autocomplete, LSP, multi-cursor, find and replace ข้ามไฟล์, การรัน git ที่เขียน
(commit, checkout, stage) และ merge conflict UI

`git` ที่ **agent** เรียกเองได้เป็นเรื่องของ spec 2.5 สเปคนี้ให้เฉพาะ endpoint อ่าน
ที่ UI เรียก
