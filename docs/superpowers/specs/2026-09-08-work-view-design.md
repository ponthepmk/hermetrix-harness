# Work view — design

วันที่ตกลง: 2026-09-08
สถานะ: spec รอ implement
ขอบเขต: spec ที่ 3 จาก 4 · มุมมอง Work ตาม [spec 1](2026-09-01-shell-and-project-design.md) §3.1

## 1. ปัญหา

`data-view="work"` มีอยู่บน header ตั้งแต่ spec 1 ลง กดแล้วได้ข้อความว่า
"Not built yet. Waiting on spec 3" มาตลอด — ซื่อสัตย์แต่ไม่มีประโยชน์

spec 1 จองที่ไว้ให้แล้ว: rail = บอร์ดและฟิลเตอร์ · main = kanban · side = รายละเอียดงาน
สเปคนี้เติมเนื้อในที่จองไว้

## 2. สิ่งที่ตัดสินแล้ว

**Work แสดงงานที่ระบบรู้จักอยู่แล้ว ไม่ใช่ระบบ to-do ที่ผู้ใช้พิมพ์เอง**

เหตุผล: งานใน Hermetrix เกิดจากการทำงานจริง ไม่ได้เกิดจากการพิมพ์รายการ —
team run สร้าง task ตาม DAG · `workspace.run` สร้าง background job ·
tool ที่ต้องอนุมัติสร้างงานที่รอคน กระดานที่พิมพ์การ์ดเองจะเป็นรายการที่สองที่ไม่มีใครอัปเดต
และวันหนึ่งมันจะขัดกับสถานะจริง

ทางเลือกที่ปฏิเสธ: **kanban ที่ลากการ์ดเปลี่ยนสถานะได้** — สถานะของ task มาจาก
DAG ที่กำลังรัน การลากการ์ดจาก `running` ไป `completed` ด้วยมือคือการโกหกเกี่ยวกับ
สิ่งที่เครื่องทำจริง ระบบนี้มี `uncertain-not-success` เป็นหลักการอยู่แล้ว การลากสถานะขัดกับมันตรงๆ

**สิ่งที่ลากได้คือลำดับความสนใจของคน ไม่ใช่สถานะของเครื่อง** — ดู §4.3

## 3. แหล่งข้อมูล — มีของอยู่แล้วทั้งหมด

| การ์ดบนกระดาน | มาจาก | endpoint |
|---|---|---|
| งานของทีม | `agent_team_tasks` (มี `state`, `depends_json`, `session_id`, token) | `GET /api/team-runs/{id}` |
| รอบการรัน | `agent_team_runs` | `GET /api/team-runs` |
| งานเบื้องหลัง | `background_jobs` (`kind` = command, export, import, browser_screenshot…) | `GET /api/jobs` |
| งานที่รอคนอนุมัติ | approval ของ task | `POST /api/team-runs/{id}/tasks/{task}/approval` |

**ไม่ต้องเพิ่มตารางใหม่ ไม่ต้องเพิ่ม endpoint ใหม่** สำหรับ v1

คำศัพท์สถานะที่มีจริงในโค้ด: `queued` `running` `blocked` `awaiting_approval`
`resolving_approval` `completed` `failed` `cancelled`

## 4. โครงจอ

### 4.1 คอลัมน์

สี่คอลัมน์ ยุบจากสถานะจริงแปดตัว เพราะแปดคอลัมน์บนจอเดียวอ่านไม่ออก:

```
รอเริ่ม          queued
กำลังทำ         running · resolving_approval
รอคุณ           awaiting_approval · blocked
จบแล้ว          completed · failed · cancelled
```

**"รอคุณ" อยู่คอลัมน์ที่สาม ไม่ใช่ท้ายสุด** เพราะมันคือคอลัมน์เดียวที่การกระทำของคน
เปลี่ยนผลลัพธ์ได้ ถ้าอยู่ท้ายจะถูกอ่านหลังสุดหรือไม่ถูกอ่านเลย

การ์ด `failed` แสดงสีสถานะ `--danger` และไม่ถูกยุบรวมกับ `completed` ในสายตา
แม้อยู่คอลัมน์เดียวกัน

### 4.2 rail — บอร์ดและฟิลเตอร์

- เลือกแหล่ง: **ทีม** (แต่ละ run) · **งานเบื้องหลัง** · **ทั้งหมด**
- ฟิลเตอร์: เฉพาะที่รอฉัน · เฉพาะที่ล้มเหลว · ช่วงเวลา
- ตัวนับต่อคอลัมน์ นับจากของจริง ไม่ใช่ค่าที่ hardcode (กฎเดิมจาก spec 1 §3.5)

### 4.3 การจัดลำดับ

ในคอลัมน์ ลากการ์ดสลับลำดับได้ = **ลำดับความสนใจของคน** เก็บใน `localStorage`
ต่อโปรเจค เหมือน layout (spec 1 §3.4) ไม่เขียนกลับไปที่ `agent_team_tasks`

ลากข้ามคอลัมน์ **ไม่ได้** — คอลัมน์คือสถานะจริงของเครื่อง ปล่อยการ์ดจะเด้งกลับ
พร้อมข้อความว่าทำไม ไม่ใช่เงียบๆ

### 4.4 side — รายละเอียดงาน

การ์ดที่เลือก แสดง: prompt เต็ม · member ที่รับผิดชอบ · งานที่มันรอ (`depends_json`) ·
token ที่ใช้ · error เต็มถ้าล้มเหลว · ปุ่มไปยัง session ที่ทำงานนั้น (`session_id`) ·
ปุ่มอนุมัติ/ปฏิเสธถ้าอยู่ `awaiting_approval`

**การอนุมัติจากที่นี่ต้องผ่านสัญญาเดิมทุกข้อ** — exact revision, effect preview,
receipt (spec 1 §9.3 และ `TestCapabilityPickerPreservesSessionAndApprovalContracts`)
จอนี้เป็นทางเข้าที่สอง ไม่ใช่ทางลัด

## 5. panel `task` ใน Chat

มุมมอง Chat มี panel ย่อชื่อ `task` ใน side: แสดงเฉพาะ **"รอคุณ" กับ "กำลังทำ"**
ของโปรเจคนี้ นับได้ กดแล้วกระโดดไป Work view

เหตุผล: ระหว่างคุยอยู่ ผู้ใช้ต้องรู้ว่ามีอะไรค้างรอตัวเอง แต่ไม่ต้องเห็นกระดานทั้งใบ
กระดานเต็มต้องการความกว้าง — เป็นเหตุผลเดียวกับที่ spec 1 ย้าย terminal ออกจาก side 320px

## 6. Error handling

- ไม่มี team run และไม่มี job เลย: บอกว่ายังไม่มีงาน พร้อมบอกว่างานเกิดจากอะไร
  (รันทีม / `workspace.run`) ไม่ใช่กระดานว่างเปล่าที่ไม่บอกอะไร
- run ถูกลบระหว่างเปิดอยู่: การ์ดหายพร้อมข้อความ ไม่ค้างเป็นการ์ดผี
- อนุมัติแล้วล้มเหลว: ข้อความอยู่ติดปุ่ม ไม่ใช่ toast (spec 1 §8)
- polling ล้มเหลว: บอกว่าข้อมูลเก่าแค่ไหน ไม่ใช่แสดงค่าเดิมเงียบๆ เหมือนยังสด

## 7. Testing

- `web`: `/api/team-runs` และ `/api/jobs` ที่ Work ใช้ ส่งฟิลด์ที่จอต้องใช้ครบ
  และไม่ส่งตัวนับที่ยังไม่มีระบบรองรับ
- `ui_contract_test`: มุมมอง Work ไม่มีข้อความ "Not built yet" เหลืออยู่ ·
  ทุก id ที่เพิ่มถูก bind · ไม่มี `.style.` เพิ่ม
- คอลัมน์: สถานะแปดตัวยุบเป็นสี่คอลัมน์ครบทุกตัว ไม่มีสถานะไหนตกหล่นจนการ์ดหายจากจอ
  — mutation: ลบการ map ของ `resolving_approval` แล้ว test ต้องแดง (การ์ดหายเงียบคือบั๊กที่มองไม่เห็น)
- ลากข้ามคอลัมน์ถูกปฏิเสธพร้อมเหตุผล และ **สถานะใน DB ไม่เปลี่ยน**
- ลำดับที่ลากไว้ถูกจำต่อโปรเจค และค่าที่เสียไม่ทำให้กระดานว่าง (กฎเดิม spec 1 §3.4)
- อนุมัติจาก Work สร้าง receipt เดียวกับอนุมัติจาก Chat — เทียบ receipt สองทางแล้วต้องเท่ากัน

## 8. นอกขอบเขต

- การ์ดที่ผู้ใช้สร้างเอง / backlog ที่พิมพ์เอง — ต้องมีตารางใหม่ ยังไม่มีหลักฐานว่าจำเป็น
- ผูกงานกับข้อความในแชทแบบสองทาง (spec 1 เขียนว่า "linking work to chat")
  v1 ทำทางเดียว: การ์ด → session ที่ทำงานนั้น
- แจ้งเตือนเมื่อมีงานเข้า "รอคุณ"
