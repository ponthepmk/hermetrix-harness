# Shell and Project — design

วันที่ตกลง: 2026-09-01
สถานะ: spec รอ implement
ขอบเขต: spec ที่ 1 จาก 4 · อีกสามอันคือ Code view, Work, Knowledge

## 1. ปัญหา

ทุกอย่างที่เพิ่มเข้ามาถูกต่อเติมลงในโครงที่ไม่ได้ออกแบบมารองรับ แต่ละคำขอได้คำตอบที่ดีเฉพาะจุด
แต่ภาพรวมไม่เคยถูกออกแบบ ผลคือแก้ทีละจุดแล้วยังรู้สึกว่า "ดีขึ้นแต่ยังยาก"

หลักฐานสามข้อ:

- **Code door ไม่ใช่ที่เขียนโค้ด** — `internal/web/ui/app.js` บรรทัดที่ door `code` ทำงาน
  มีคำสั่งเดียวคือ `switchWorkbench("files")` ซึ่งเปิด panel ไฟล์กว้าง 320-430px ใน inspector
  ขวา ไม่มี editor ไม่มี tab ไม่มี diff และพื้นที่หลักยังเป็นแชทอยู่
- **Project อยู่ผิดที่** — อยู่ใน Settings → System → Projects ทั้งที่ทุก session ผูกกับ project
  และเป็นสิ่งแรกที่ต้องเลือกก่อนทำงาน มันถูกจัดเป็น configuration ทั้งที่มันคือ workspace
- **พื้นที่หลักแสดงได้อย่างเดียว** — `#view-chat` เป็น view เดียวที่อยู่ใน `.reading-card`
  ที่เหลือทั้งหมดถูกย้ายไปอยู่ใน settings overlay หรือ inspector 320px ไม่มี "ที่ที่สาม"

## 2. สิ่งที่ตัดสินแล้ว

**Project คือขอบเขตงาน ไม่ใช่โฟลเดอร์โค้ด** โปรเจคโค้ดมี root โปรเจคชีวิตประจำวันไม่มี
โครงสร้างเดียวกัน ไม่มีข้อยกเว้น เพราะการวางแผนเที่ยวกับการวางแผน refactor มีรูปร่างเดียวกัน:
ขอบเขตหนึ่งที่มีงาน มีโน้ต มีบทสนทนา ต่างกันแค่มีไฟล์หรือไม่ นั่นคือ field ไม่ใช่ type

ทางเลือกที่ปฏิเสธ: **Workspace ครอบ Project** ทำให้ทุกการกระทำต้องตอบสองคำถามก่อนเริ่ม
("workspace ไหน แล้ว project ไหน") ซึ่งเป็นปัญหาเดียวกับเมนู 19 ช่องที่เพิ่งแก้ไป

**เปิดโปรแกรมมาต้องเห็น project picker** เจ้าของเลือกข้อนี้เอง shell จึงมี project เป็นราก

## 3. โครงจอ

### 3.1 เขตที่ปรับขนาดได้

```
┌─────────────────────────────────────────────────────────┐
│ [● project ▾]   Work Chat Code Knowledge      ⌕ ⇔ ⚙   │  header 46px คงที่
├────────╥──────────────────────────────╥─────────────────┤
│ rail   ║           main               ║      side       │
│        ║   แบ่งเป็น pane ย่อยได้       ║                 │
│ 220px  ║   สูงสุด 2 คอลัมน์ × 2 แถว     ║     320px       │
│        ║                              ║                 │
└────────╨──────────────────────────────╨─────────────────┘
   ╥ = ที่จับลาก · ทุกเขตย่อ/ขยาย/ซ่อนได้
```

หน้าที่ของแต่ละเขตไม่เปลี่ยนตามมุมมอง เนื้อหาเปลี่ยน ความหมายไม่เปลี่ยน:

| มุมมอง | rail = รายการ | main = ตัวงาน | side = หลักฐาน |
|---|---|---|---|
| Work | บอร์ดและฟิลเตอร์ | kanban | รายละเอียดงานและสิ่งที่ผูกอยู่ |
| Chat | แชทและงานที่ผูก | บทสนทนา | Review, Files, Office, Team |
| Code | file tree และ diff | editor + pane ที่แบ่งเอง | เหตุผลที่แก้ ผลเทสต์ |
| Knowledge | คลังและที่มา | ค้นหาและโน้ต | โน้ตที่เลือกและ backlink |

**ตัวสลับมุมมองมีอันเดียว อยู่บน header** rail จึงเป็นพื้นที่ของเนื้อหา ไม่ใช่เมนู
ปัญหาเดิมคือ rail แบกทั้งเมนู ทั้ง session dock ทั้ง settings จนไม่เหลือที่

### 3.2 ทำไมไม่ใช่ panel ตายตัว

ร่างแรกวาง Terminal กับ Browser ไว้ใน side 320px นั่นคือความผิดพลาดเดียวกับที่สเปคนี้
ยกมาเป็นปัญหาข้อแรก: file panel 320px ที่อ่านโค้ดไม่ได้ terminal ที่กว้าง 320px
ก็ใช้งานไม่ได้ด้วยเหตุผลเดียวกัน

กฎที่ตามมา: **ถ้าเนื้อหาต้องการพื้นที่ ผู้ใช้ต้องให้พื้นที่มันได้** ไม่ใช่ผู้ออกแบบเดาไว้ล่วงหน้า

### 3.3 การแบ่ง pane

- ทุกเส้นแบ่งระหว่างเขตเป็น **ที่จับลาก** ปรับความกว้างได้
- rail และ side **ซ่อนได้** (`⇔` บน header ซ่อน side, ปุ่มบน rail ซ่อน rail)
- **main แบ่งเป็น pane ย่อยได้** สูงสุด 2 คอลัมน์ × 2 แถว
  - ทำไมจำกัดที่ 4: มากกว่านี้แต่ละช่องเล็กเกินกว่าจะทำงานได้บนจอเดียว
    และเป็นเพดานที่ทดสอบได้จริง ไม่ใช่ tiling ที่ไม่มีขอบเขต
- แต่ละ pane เลือกเนื้อหาเองจากรายการเดียวกัน: **Editor · Diff · Terminal · Browser ·
  Preview · Output** เนื้อหาไม่ผูกกับตำแหน่ง
- แต่ละ pane **ขยายเต็ม main ได้** (ปุ่มบนหัว pane) และกลับคืนได้
- Terminal และ Browser จึงเป็น **เนื้อหาของ pane** ไม่ใช่ห้องใน side ที่ถูกบีบไว้ 320px

### 3.4 การจำ layout

ขนาดและการแบ่ง pane เก็บ **ต่อโปรเจค ต่อมุมมอง** ใน `localStorage`
- ไม่เก็บใน SQLite: มันคือความชอบของหน้าจอเครื่องนี้ ไม่ใช่ข้อมูลของโปรเจค
  และการ export/backup ไม่ควรพก layout ของใครไปด้วย
- อ่านไม่ได้หรือค่าเสีย ให้กลับไปใช้ค่าเริ่มต้นเงียบๆ ไม่ใช่จอว่าง
- ห้ามใช้ inline style ในการปรับขนาด — server ส่ง `style-src 'self'` อยู่
  ขนาดต้องผ่าน CSS custom property บน element ที่มี class เท่านั้น

### 3.5 Project picker

จอแรกเมื่อยังไม่ได้เลือกโปรเจค และเป็นจอที่กลับมาได้จากการกดชื่อโปรเจคบน header

- ค้นหาอยู่บนสุด พิมพ์ชื่อที่ยังไม่มีแล้วสร้างได้จากช่องเดียวกัน
- **ปักหมุด** แล้ว **ล่าสุด** เป็นสองกลุ่ม กลุ่มที่ว่างไม่วาด
- การ์ดแต่ละใบบอก: ชื่อ, root (หรือ "ไม่มีโฟลเดอร์โค้ด") และตัวนับ**เฉพาะที่มีระบบอยู่จริง**
  ในเฟสนี้คือจำนวนแชทเท่านั้น งานค้างและโน้ตจะปรากฏเมื่อ spec 3 และ 4 ลงแล้ว
  (mockup วาดครบสามตัวเพื่อให้เห็นปลายทาง ไม่ใช่สิ่งที่เฟสนี้ส่งมอบ)
- เนื้อหาอยู่กลางจอ ระยะซ้ายเท่าระยะขวา

## 4. Data model

### 4.1 การเปลี่ยน schema

`projects.root_path` เป็น `TEXT NOT NULL UNIQUE` ซึ่งรับค่าว่างได้แค่แถวเดียว
โปรเจคที่ไม่มีโค้ดหลายอันจะชนกันทันที SQLite ลบ UNIQUE ออกจากคอลัมน์ไม่ได้
ต้อง **rebuild ตาราง** ใน `schemaV29`:

```sql
CREATE TABLE projects_new (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL UNIQUE,
  root_path TEXT NOT NULL DEFAULT '',   -- ว่าง = โปรเจคที่ไม่มีโค้ด
  state TEXT NOT NULL DEFAULT 'active',
  pinned INTEGER NOT NULL DEFAULT 0,
  last_opened_at TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
INSERT INTO projects_new(id,name,root_path,state,created_at,updated_at)
  SELECT id,name,root_path,state,created_at,updated_at FROM projects;
DROP TABLE projects;
ALTER TABLE projects_new RENAME TO projects;
-- UNIQUE เฉพาะ root ที่มีจริง: โปรเจคไม่มีโค้ดกี่อันก็ได้
CREATE UNIQUE INDEX idx_projects_root ON projects(root_path) WHERE root_path <> '';
```

`last_opened_at` และ `pinned` มีไว้ให้ picker เรียงได้โดยไม่ต้องเดา

### 4.2 กฎของ root

`resolveProjectRoot` ปัจจุบันบังคับว่าต้องเป็นไดเรกทอรีที่มีอยู่จริง กฎใหม่:

- root ว่าง = โปรเจคไม่มีโค้ด ยอมรับ
- root ไม่ว่าง = ต้องเป็น absolute path, resolve symlink, ต้องเป็นไดเรกทอรีที่มีอยู่ (กฎเดิมทั้งหมด)

เครื่องมือที่ต้องใช้ root (files, terminal, browser, command) ต้อง **ปฏิเสธอย่างชัดเจน**
เมื่อโปรเจคไม่มี root ไม่ใช่ fallback ไปที่ working directory ของ server
ข้อความต้องบอกว่าโปรเจคนี้ไม่มีโฟลเดอร์โค้ด ไม่ใช่ "path ไม่ถูกต้อง"

### 4.3 API

| Method | Path | ทำอะไร |
|---|---|---|
| GET | `/api/projects` | เพิ่ม `pinned`, `last_opened_at`, และตัวนับ (sessions) ใน response |
| POST | `/api/projects/{id}/open` | บันทึก `last_opened_at` คืน project |
| PUT | `/api/projects/{id}/pin` | `{pinned: bool}` |

ตัวนับงานและโน้ตยังไม่มีในเฟสนี้ (spec 3 และ 4) จึงไม่ส่ง ไม่ใช่ส่งเลข 0
**หมวดที่ว่างเปล่าห้ามวาด** — การ์ดจะไม่แสดงบรรทัดที่ยังไม่มีระบบอยู่ข้างหลัง

### 4.4 สองกรณีที่ต้องมีคำตอบชัด

**session เดิมที่ไม่มีโปรเจค** ทุกวันนี้ `project_id` เป็นค่าว่างได้ ("chat only") เมื่อ project
กลายเป็นราก session เหล่านั้นจะไม่มีที่ยืน คำตอบ: ตอน migrate ให้ผูกกับโปรเจคชื่อ
`Inbox` ที่สร้างอัตโนมัติและไม่มี root ไม่ลบและไม่ซ่อน session ใดทั้งสิ้น
`Inbox` เป็นโปรเจคปกติทุกประการ ลบเองได้ถ้าว่าง

**โปรเจคที่ลงทะเบียนตอน start** `EnsureWorkspaceProject` ยังทำงานเหมือนเดิม
`--workspace` ยังลงทะเบียน root นั้นเป็นโปรเจคและ pin ให้อัตโนมัติ เพื่อให้เปิดมาแล้ว
เจอโปรเจคที่ตั้งใจทำงานด้วยอยู่บนสุดของ picker

## 5. สิ่งที่ย้ายและสิ่งที่อยู่ที่เดิม

**ย้าย:**
- Projects ออกจาก Settings → กลายเป็น picker และ header
- Chat จาก `.reading-card` → main ของมุมมอง Chat
- session dock จาก rail กลาง → rail ของมุมมอง Chat
- workbench rooms ที่เหลือ (Review, Files, Office, Team) จาก inspector → side ของมุมมอง Chat
- **Terminal และ Browser ออกจาก workbench room → เป็นเนื้อหาของ pane** เลือกได้ทุกมุมมอง
  ไม่ใช่ห้องกว้าง 320px อีกต่อไป (backend เดิมใช้ได้ทั้งหมด ไม่แตะ)
- doors Assistant/Code/Team → **ยกเลิก** ถูกแทนที่ด้วยมุมมอง Work/Chat/Code/Knowledge
  (door เดิมทำได้แค่สลับห้องใน inspector ไม่ใช่วิธีทำงานที่ต่างกันจริง)

**อยู่ที่เดิม ไม่แตะ:**
- Settings overlay ทั้งหมด (`CONFIG_SECTIONS`, nav, search) — เพิ่งออกแบบใหม่และใช้งานได้
- command palette `⌘K` — เพิ่ม "ไปที่โปรเจค…" และมุมมองทั้งสี่เข้าไป
- capability picker, density toggle, composer keys
- API และ backend ทั้งหมดของ chat, files, terminal, browser, MCP, skills

**ยังไม่ทำในเฟสนี้:** มุมมอง Work, Knowledge และ Code แสดงเป็นสถานะ "ยังไม่ได้สร้าง"
พร้อมบอกว่าอยู่ใน spec ไหน ไม่ใช่แท็บว่างที่กดแล้วไม่มีอะไร

## 6. Error handling

- โปรเจคถูกลบหรือ root หายไประหว่างใช้งาน: header แสดงสถานะ ไม่ crash และ picker
  ยังเปิดได้เสมอ
- ไม่มีโปรเจคเลย: picker แสดงเฉพาะช่องค้นหาและปุ่มสร้าง ไม่วาดหมวดที่ว่าง
- เปิดมุมมองที่ยังไม่ได้สร้าง: บอกตรงๆ ว่ายังไม่มี ไม่ใช่หน้าว่าง

## 7. Testing

- `store`: migration v29 รักษาข้อมูลเดิม, โปรเจคไม่มี root หลายอันอยู่ร่วมกันได้,
  โปรเจคที่มี root ซ้ำกันยังถูกปฏิเสธ
- `product`: `resolveProjectRoot` รับค่าว่าง, ปฏิเสธ path ที่ไม่มีจริง,
  เครื่องมือที่ต้องใช้ root ปฏิเสธพร้อมข้อความที่บอกสาเหตุจริง
- `web`: `/open` และ `/pin` เปลี่ยนสถานะจริง, listing ไม่ส่งตัวนับที่ยังไม่มีระบบ
- `ui_contract_test`: header มีตัวสลับมุมมองอันเดียว, picker เป็น element จริง,
  ทุก id ที่เพิ่มถูก bind (กฎเดิมของไฟล์นี้)
- ตรวจในเบราว์เซอร์จริงที่ 1280×800 และ 1600×1000: ไม่มี horizontal overflow ทุกมุมมอง
- pane: ลากปรับขนาดแล้วค่าถูกจำ, ปิดเปิดใหม่ layout กลับมาเหมือนเดิม, ค่าที่เสียไม่ทำให้จอว่าง,
  แบ่งครบ 4 ช่องแล้วยังไม่ overflow, ขยายเต็มแล้วกลับคืนได้
- ไม่มี `.style.` เพิ่มใน `app.js` (กฎเดิมของ `ui_contract_test`) — การปรับขนาดต้องผ่าน
  CSS custom property

## 8. นอกขอบเขต spec นี้

แผนเดิม 4 spec ขยายเป็น 6 หลังจากตรวจพบว่า agent ยังรันอะไรไม่ได้เลย

| # | Spec | สาระ |
|---|---|---|
| 2 | Code view | editor จริง, syntax highlight, diff renderer, tab ไฟล์ |
| **2.5** | **Agent runtime tools** | ให้ agent รันคำสั่งและขับ browser ได้ |
| 3 | Work | schema งาน, kanban, ผูกงานกับแชท |
| **3.5** | **QC และ load testing** | วางแผนทดสอบ, รัน, เก็บผล — ต่อยอดจาก 2.5 และ teams ที่มีอยู่ |
| 4 | Knowledge | schema โน้ต, ค้นหาเชิงความหมาย, tool ให้ agent เขียน/ค้นโน้ต |
| **5** | **Voice conversation** | คุยโต้ตอบด้วยเสียงสองทาง near-realtime ทำได้หลัง spec 1 |

### 8.1 ช่องว่างที่ค้นพบระหว่างเขียนสเปคนี้

Direct tool waist ทั้ง 11 ตัวคือ `context_search`, `skill_search`, `skill_view`,
`skill_manage`, `tool_call`, `tool_describe`, `tool_search` และ `workspace.*` สี่ตัว

**ไม่มี terminal ไม่มี browser ไม่มี command** — ทั้งสองอย่างมีจริงและทำงานได้ แต่ขับได้จาก
UI เท่านั้น (`internal/tools/registry.go` ไม่มีคำว่า browser เลย) แปลว่า agent อ่านและ
เขียนไฟล์ได้ แต่ **รันเทสต์ไม่ได้และดูหน้าเว็บไม่ได้**

agent ที่ตรวจงานตัวเองไม่ได้ ไม่ใช่เครื่องมือเขียนโค้ด และ QC กับ load test ต่อยอดจาก
ช่องว่างนี้ไม่ได้เลย spec 2.5 จึงต้องมาก่อน 3.5 — QC ที่รันเทสต์ไม่ได้คือเอกสาร ไม่ใช่ QC

### 8.2 ราคาที่รู้ล่วงหน้า

**waist จะโต** ตอนนี้ 11 spec 2.5 เพิ่ม command และ browser tool spec 4 เพิ่ม note tool
ทุก request จ่ายค่านี้ตลอด ทางเลือกคือยัดบางตัวเข้า deferred catalog แบบเดียวกับ MCP
resources ซึ่ง waist ไม่โต ตัดสินในสเปคนั้นๆ ไม่ใช่ที่นี่

**การให้ agent รันคำสั่งคือการขยาย authority** ต้องผ่าน approval gate และ allowlist
เดียวกับที่ `internal/product/commands.go` ใช้อยู่ ไม่ใช่ shell เปล่า

**dependency ก้อนใหญ่ที่ต้องตัดสินใน spec 2** UI ตอนนี้เป็น vanilla JS ไฟล์เดียว ไม่มี
build step การใส่ CodeMirror หรือ Monaco เปลี่ยนข้อนี้ ต้องชั่งกับการเขียน highlighter
เองแบบจำกัดภาษา

### 8.3 authority ของ spec 2.5 ที่ตกลงแล้ว

ตัดสินไว้ที่นี่เพราะเป็นการขยาย authority และไม่ควรถูกตัดสินใหม่ตอนเขียนโค้ด

**รันคำสั่ง** ใช้ allowlist เดิมที่ `internal/product/commands.go` ใช้อยู่แล้ว
(`go`, `git`, `node`, `npm`, `python3`, `rg`, `ls`) และ **ไม่ต้องขออนุมัติรายครั้ง**

เหตุผลที่ไม่ขอ: agent ที่ต้องขออนุญาตทุกครั้งที่จะรันเทสต์ จะไม่รันเทสต์ ซึ่งทำให้
มันกลับไปเป็น agent ที่ตรวจงานตัวเองไม่ได้เหมือนเดิม สิ่งที่ทำให้ปลอดภัยคือ**ขอบเขต**
ไม่ใช่การถาม: executable ที่ระบุชื่อได้ · working directory ผูกกับ project root ·
environment จำกัดไม่มี secret · deadline 1-120 วินาที · output เพดาน 2 MiB ·
ยกเลิกได้ทั้ง process group · receipt เป็น artifact ที่ลบไม่ได้

ข้อจำกัดที่ต้องเขียนไว้ตรงๆ: นี่คือ process hardening **ไม่ใช่ OS sandbox**
คำสั่งที่อยู่ใน allowlist ยังรันโค้ดที่อยู่ใน repo ได้ (`go test` รัน test ที่ repo เขียนไว้)
ถ้าจะเปิด repo ที่ไม่ไว้ใจ ต้องรันทั้ง Hermetrix ใน container

**ขับ browser** loopback รันได้เลย · **URL ภายนอกต้องขออนุมัติ**

เหตุผล: ตรวจ UI ที่ตัวเองเพิ่งแก้คือเหตุผลหลักที่ agent ต้องมี browser และมันอยู่บน
localhost เสมอ ส่วนเน็ตข้างนอกเป็นคนละเรื่อง

**เนื้อหาหน้าเว็บเป็น untrusted evidence เสมอ** ไม่ว่ามาจาก loopback หรือข้างนอก
กฎนี้มีอยู่แล้วใน managed browser ปัจจุบัน (DOM snapshot ถูกติดป้าย) และต้องคงไว้:
ข้อความบนหน้าเว็บที่สั่งให้ agent ทำอะไร คือข้อมูล ไม่ใช่คำสั่ง เหตุผลที่ข้อนี้สำคัญขึ้น
เมื่อ agent เป็นคนขับเอง คือ agent เป็นผู้อ่านคนแรก ไม่ใช่ผู้ใช้

### 8.4 เสียง: คุยโต้ตอบสองทาง (spec 5)

ร่างแรกจัดเสียงไว้ว่า "เล็ก แทรกได้ทุกจุด" ซึ่งผิด สิ่งที่เจ้าของขอคือ **คุยโต้ตอบ**
ไม่ใช่พิมพ์ด้วยเสียง นั่นคือ STT ขาเข้า TTS ขาออก และเวลาแฝงที่ต่ำพอจะเรียกว่าคุย
มันจึงเป็นสเปคเต็มตัว

**ทั้งหมดประมวลผลในเครื่อง** `webkitSpeechRecognition` ของ Chrome ส่งเสียงขึ้น server
ของ Google จึงใช้ไม่ได้กับระบบที่ยึด local-first ทั้ง STT และ TTS เป็น endpoint ที่ผู้ใช้
ตั้งเอง รูปแบบเดียวกับ provider และ embeddings: Hermetrix เก็บแค่ URL ไม่เก็บโมเดล
**ไม่มี endpoint = ปุ่มไมค์ไม่ปรากฏ** ไม่ใช่ปรากฏแล้วกดไม่ได้ (หมวดที่ว่างเปล่าห้ามวาด)

**เวลาแฝงคือหัวใจ** ถ้ารอคำตอบจบแล้วค่อยพูด จะช้าเกินกว่าจะเป็นบทสนทนา
ท่อที่ต้องใช้มีอยู่แล้ว: `consumeAgentStream` ส่ง delta ทีละ token อยู่ตอนนี้
TTS ต้องตัดเป็นประโยคจาก stream นั้นและส่งไปสังเคราะห์ทีละประโยค ไม่ใช่รอทั้งเทิร์น

**Hands-free** VAD ทำงานในเบราว์เซอร์ ฟังตลอดเมื่อเปิดโหมดเสียง และ **แทรกกลางคันได้**:
ผู้ใช้พูดขณะ agent กำลังพูด ต้องหยุดเสียงทันทีและทิ้งเสียงที่ค้างอยู่ในคิว
ไม่ใช่พูดต่อจนจบประโยค

ราคาที่ยอมรับ: false trigger จากเสียงรอบข้าง จึงต้องมี **สวิตช์ปิดไมค์ที่เห็นชัดตลอดเวลา**
และตัวบอกสถานะว่ากำลังฟังอยู่หรือไม่ สถานะไมค์ต้องรู้ได้จากสีและจากคำ ไม่ใช่จากการ
เคลื่อนไหวอย่างเดียว

**อ่านอะไรไม่อ่านอะไร** เสียงอ่าน**ข้อความ**เท่านั้น

| เจอ | เสียงทำอะไร |
|---|---|
| ข้อความธรรมดา | อ่าน |
| โค้ดและ diff | ข้าม พูดแทนว่าแก้ไฟล์อะไร กี่บรรทัด |
| tool call | สรุปหนึ่งบรรทัด ไม่อ่าน argument |
| รออนุมัติ | **พูดว่ารออะไรอยู่** และหยุด ไม่ใช่เงียบไปเฉยๆ |
| elicitation จาก MCP | อ่านคำถามและรอคำตอบด้วยเสียง |

เหตุผลข้อ "รออนุมัติต้องพูด": ในโหมดเสียงผู้ใช้อาจไม่ได้มองจอ agent ที่หยุดรอ
เงียบๆ จะดูเหมือนค้าง

**ยังไม่ตัดสินในสเปคนี้** เลือก VAD library อะไร, whisper แบบ streaming หรือ chunk,
TTS ตัวไหน และรูปแบบ endpoint — เป็นเรื่องของ spec 5
