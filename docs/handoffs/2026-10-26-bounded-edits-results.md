# ผลตรวจการประกอบ exact edits ภายในส่วนไฟล์

วันที่ 26 ตุลาคม 2026 · ขั้น H1D-A2

สถานะ: Hermetrix นำเข้า 9 ไฟล์ผ่าน native API แล้ว มี mutation receipts 9 รายการ ไม่มี rollback รีวิวแยกอนุมัติโดยไม่มี finding ค้าง และทดสอบจากไฟล์จริงใน workspace พร้อม build ผ่านแล้ว ใช้โมเดลเดิมแยกอีกครั้ง จึงไม่มีข้ออ้างเรื่องความหลากหลายของโมเดล

ชุดงานประกอบด้วย production helper ใหม่ `internal/worker/file_views_edits.go` และ tests 8 ไฟล์ รวม 9 ฟังก์ชันทดสอบ Codex กำหนดสัญญา ข้อมูลตั้งต้น ตรวจข้อเสนอและเรียก API เดิม ส่วน implementation และ tests มาจาก Hermetrix ที่เรียก Bonsai Local จริง การจัดรูปแบบใช้ gofmt เท่านั้น ดู [สัญญางาน](2026-10-26-bounded-file-views-contract.md)

## พฤติกรรมที่ตรวจได้

`MaterializeBoundedChange` รับ source เต็มและ hash ที่คาดไว้แยกจาก views ตรวจทุก view ก่อนใช้ แล้วรับเฉพาะ exact old/new edits ภายในช่วงเดียวที่ให้มา ผลสำเร็จคืน source เต็มกับ strategy `replace_text` ไม่อ่านหรือเขียน filesystem และไม่เปลี่ยน slices ของ caller

| เกณฑ์ | ผลบนข้อเสนอสุดท้าย |
| --- | --- |
| ข้อมูลส่วนไฟล์ | รับ 1–32 views; ปฏิเสธ view ซ้ำ ช่วงที่มีความยาวและซ้อนกัน และ metadata ที่ไม่ตรง |
| ช่วงติดกันและช่วงว่าง | ช่วงติดกันได้ แต่ห้าม edit คร่อมสองช่วง; ช่วงว่างที่ไม่ได้ใช้ผ่านได้และไม่ให้อำนาจแก้ข้อความ |
| รูปแบบการแก้ | ต้องไม่มี replacement content และมี 1–64 edits; Old ห้ามว่าง และ Old/New ต้องเป็น UTF8 |
| การจับคู่ข้อความ | ต้องมี Old เพียงครั้งเดียวใน preimage เต็มเดิม รวมการปรากฏที่ซ้อนกัน เช่น `aaaa` กับ `aaa` |
| หลาย edits | จับตำแหน่งจาก source เดิมทั้งหมด ปฏิเสธ edits ซ้อนกันหรือ chain ผ่านข้อความที่เพิ่งสร้าง แล้วประกอบย้อนลำดับตำแหน่ง |
| การรักษา source | ตรวจข้อความเต็มที่คาดไว้ รวมส่วนที่ไม่ได้ให้แก้, Unicode, CRLF, deletion และ no-op |
| ขอบเขตจำนวน | 64 edits และ 32 views ผ่าน; 65 edits ที่แต่ละรายการจับคู่ได้จริง, 33 views ที่ไม่ซ้อนกัน และ zero views ถูกปฏิเสธ |
| Error | คืน content/strategy ว่าง และแนะนำการซ่อมที่อยู่ในขอบเขตจริง |
| ชุดทดสอบ | worker ทั้ง package และ go vet ผ่าน; focused suite 9 ฟังก์ชันผ่าน |
| ไฟล์จริงหลังนำเข้า | worker และ skills ผ่าน; build cmd/hermetrix ผ่าน; binary ใหม่ยังไม่ได้เปิด |
| การผูกฉบับรีวิว | source ของ H1B, A1 และ A2 รวม 25 ไฟล์ ตรงกับ hash ฉบับรีวิวครบ |

ดู [receipt และขอบเขตที่พิสูจน์](../evidence/2026-10-26/h1d-live/H1D-A2-receipt.json) พร้อม [บันทึกงานโมเดล](../evidence/2026-10-26/h1d-live/H1D-A2-job-ledger.json) การตรวจจาก source จริงหลังนำเข้ายืนยันว่า agent/service.go ขนาด 172,056 bytes ยังถูกปฏิเสธก่อน provider ด้วยเพดาน 128 KiB ตามเดิม

กลุ่มกรณีตรวจมีบางส่วนซ้ำกัน จึงไม่บวกเป็นจำนวนข้อกำหนดที่ไม่ซ้ำ และไม่ใช้ผลชุดนี้เป็นตัวเลขความแม่นยำทั่วไปของโมเดล

## สิ่งที่ล้มเหลวและวิธีตรวจ

ข้อเสนอแรกคอมไพล์ไม่ผ่าน และคัดลอกสิทธิ์แทนไฟล์ทั้งก้อนจากเส้นทางเดิม ทั้งที่ bounded mode ห้ามใช้ การซ่อมหลายจุดพร้อมกันยังทิ้งตัวแปรที่ไม่ได้ใช้ จึงแยกแก้ compiler ทีละสาเหตุ ไม่รับ source รุ่นเหล่านั้นเข้า workspace

tests ที่โมเดลสร้างมีข้อผิดพลาดด้วย ได้แก่สร้าง RegionID ปลอม `r1`, import โมดูล `workerapi` ที่ไม่มีจริง, ส่ง pointer ที่ขอ replacement content แทน nil, เปรียบผล Y tokens กับ source X tokens และเรียกข้อมูล 64 edits ซ้ำแล้วระบุว่าเป็นกรณี 65 edits กรณีบวกที่ตรึงไว้ช่วยให้ข้อผิดพลาดเหล่านี้ไม่กลายเป็น false pass

กรณี source ที่ไม่ใช่ UTF8 ก็ต้องมี Old ที่จับคู่ได้จริงและ metadata สอดคล้องกัน มิฉะนั้นการหา Old ไม่เจอหรือ hash ผิดจะกลบสิ่งที่ต้องตรวจ ชุดสุดท้ายใช้ source bytes 97,255 โดย edit เฉพาะ ASCII `a` ภายใน view 0..1 พร้อม hash/RegionID ที่ตรง เพื่อให้คุณสมบัติที่ผิดคือ UTF8 ของ source เต็ม

เมื่อการซ่อม callback syntax ซ้ำยังล้มเหลว เปลี่ยนโครงสร้างเป็นการเรียกตรงหรือใช้ตัวอย่างที่ผ่านจริงเป็น sibling แทนการเดาเครื่องหมายเดิมซ้ำ ส่วน packet ที่ชนเพดาน 3,072 tokens ถูกแบ่งตามเกณฑ์เดิม ไม่ตัดเงื่อนไขทดสอบออก บางคำสั่งที่ผู้ควบคุมเขียนแน่นหรืออธิบาย API ไม่ชัดก็มีส่วนทำให้เกิดความเข้าใจผิด จึงต้องตรวจคุณภาพ packet แยกจากคุณภาพโมเดล

พบ bug ใน implementation จริงด้วย: predicate ตรวจ views ซ้อนกันปฏิเสธช่วงว่างที่อยู่ในช่วงปกติ Hermetrix แก้ให้การชนกันเกิดได้เฉพาะสองช่วงที่มีความยาว โดยยังคงปฏิเสธ duplicate views และไม่เพิ่มสิทธิ์จากช่วงว่าง

หลักฐานเก็บข้อเสนอที่ถูกปฏิเสธ คำตอบดิบ compiler/test logs และที่มาของ source แต่ละไฟล์ ไม่ได้นำส่วนที่ดูถูกต้องจากข้อเสนอที่ล้มเหลวไป apply เงียบ ๆ การรวบรวมบทเรียนนี้ยังเป็นการกำกับโดย Codex ไม่ใช่หลักฐานว่า background learner รับบทเรียน เลื่อนรุ่น และทำงานถัดไปดีขึ้นเองแล้ว

รอบ A2 มี provider observations 35 ครั้ง รวมข้อเสนอที่ถูกปฏิเสธ การซ่อม และรีวิว ใช้ prompt 109,487 tokens และ completion 43,578 tokens มี 3 ครั้งที่ชน output limit ผล 30 รายการผ่าน protocol แต่ไม่ได้หมายถึงงานที่ถูกต้อง 30 งาน ตัวเลขนี้เป็นต้นทุนของการลงมือรอบนี้ ไม่ใช่ benchmark หรืออัตราความสามารถทั่วไป แสดงว่าต้องลดต้นทุนการซ่อมด้วย packet ที่มีชนิดข้อมูลชัดเจน ตัวอย่าง API จริง และชุดตรวจจากข้อมูลที่ host ตรึง ก่อนเปิดงานยาวแบบอัตโนมัติ

## ขอบเขตที่ยังไม่ผ่าน

A1 และ A2 เป็น pure helpers เท่านั้น ยังไม่เปลี่ยน Task, provider payload, persisted-result validation หรือ coordinator ดังนั้นยังไม่ได้พิสูจน์การแก้ไฟล์เกิน 128 KiB กับโมเดลจริงครบ proposal/apply/test/review และยังไม่ได้วัด latency ของเส้นทางไฟล์ใหญ่

view ที่ตรวจข้อมูลถูกต้องไม่ได้เป็นสิทธิ์ในตัวเอง A3 ต้องให้ host ตรึง source และขอบเขต แล้วประกอบผลใหม่จาก edits เพื่อตรวจ bytes ที่ไม่ได้แสดง แม้ผู้ส่งจะคำนวณ proposal ID ใหม่ได้ ขั้น B ต้องใช้ lifecycle เดิมของ coordinator และส่งบริบทแบบจำกัดส่วนให้ reviewer ด้วย

งาน H1A, H1B ส่วน provenance/promotion, H1C, UX/UI, computer control และ marketplace/deployment ตาม execution contract ยังอยู่ในเป้าหมายเดิมทั้งหมด การทดสอบและ build ไม่ใช่การยืนยันว่าเป้าหมายเต็มเสร็จแล้ว
