# ผลการแก้การประเมินรายกรณีด้วย Hermetrix

วันที่ 26 ตุลาคม 2026

Hermetrix เขียนโค้ดแก้การคำนวณผลประเมินและสร้างชุดทดสอบ จากนั้นระบบเขียนไฟล์ของ Hermetrix นำการเปลี่ยนแปลง 9 ไฟล์เข้า workspace จริงแล้ว การปรับครั้งนี้ป้องกันคะแนนที่เพิ่มจากกรณีใหม่ไปกลบกรณีเดิมที่ทำได้แย่ลง เมื่อมีหลักฐานรายกรณีส่งเข้ามา ส่วนการรับรองที่มาของหลักฐานและความปลอดภัยของการเลื่อน Skill ยังต้องทำต่อ

Codex จัดขอบเขตงาน วิเคราะห์ผลผิดพลาด ตรวจข้อเสนอ เรียกทดสอบ และเรียกบริการเดิมของ Hermetrix ผ่านตัวเรียกงานชั่วคราว โค้ดผลิตภัณฑ์และโค้ดทดสอบทั้งหมดมาจากคำตอบของ Hermetrix มีเพียงการจัดรูปแบบด้วย gofmt ก่อนรีวิว ไม่ได้ใช้ Codex เขียน implementation แทน

## พฤติกรรมที่เปลี่ยน

เมื่อ Result มีข้อมูล ระบบต้องอ่าน JSON object ที่มี cases array แต่ละรายการต้องมี case_id ที่ไม่ว่างและไม่ซ้ำ พร้อม baseline_passed และ candidate_passed ที่เป็น boolean ทั้งคู่ ค่า false เป็นข้อมูลที่ถูกต้อง ส่วนค่าที่หายหรือเป็น null ถูกปฏิเสธ จำนวนกรณีต้องตรงกับ Tasks

ระบบคำนวณยอดผ่านใหม่จากหลักฐาน และนับทุกกรณีที่ baseline ผ่านแต่ candidate ไม่ผ่านเป็น regression แม้คะแนนรวมเท่ากัน เกณฑ์เดิมเรื่องข้อผิดพลาดจากผู้ให้บริการ จำนวนงานขั้นต่ำ และ FalseSuccessDelta ยังคงใช้หลังคำนวณ

การเรียกแบบเดิมที่ไม่มี Result ยังใช้ยอดรวมตามเดิมเพื่อคงความเข้ากันได้ นี่เป็นขั้นย่อยก่อนเชื่อมกับรันที่ host ออกให้ ไม่ใช่การรับรองว่าข้อมูลที่ส่งมานั้นเกิดจากการทดสอบจริง

## หลักฐานการทำงาน

| รายการ | ผลที่ตรวจได้ |
| --- | --- |
| ระบบเดิมกับการทดสอบฐานข้อมูลที่ตรึงไว้ | คอมไพล์ได้ แต่ตกครบ 6 กรณีตามข้อบกพร่องที่ต้องแก้ |
| ข้อเสนอหลังแก้ | ผ่าน 6 กรณีเดิม โดยไม่ลดเงื่อนไขยืนยันผล |
| ตัวอ่านหลักฐาน | ผ่าน 14 กรณีที่ต้องปฏิเสธ และ 3 กรณีที่ถูกต้อง |
| ส่วนที่เกี่ยวข้อง | skills, learning, selfimprove, taskeval, worker, agent และ web ผ่านบนข้อเสนอ |
| การตรวจ race | internal/skills ผ่านบนข้อเสนอ |
| ไฟล์จริงหลังนำเข้า | go test ./internal/skills -count=1 ผ่าน และ build cmd/hermetrix ผ่าน |
| รีวิว | รอบแยกด้วยโมเดลเดิมอนุมัติ ไม่มี finding ค้าง |
| การนำเข้าไฟล์ | WriteProjectFilesAtRoot ออก mutation receipt 9 รายการ ไม่เกิด rollback |
| ความตรงของไฟล์ | SHA-256 ของทั้ง 9 ไฟล์ตรงกับฉบับที่รีวิว |

บันทึกคำสั่งสรุป:

```text
go test ./internal/skills -count=1 -timeout 3m
ok hermetrix-harness/internal/skills 6.598s
WORKSPACE_SKILLS_EXIT=0

go build -o <run-directory>/hermetrix-H1B.exe ./cmd/hermetrix
WORKSPACE_BUILD_EXIT=0

native product apply: file_receipts=9 rollback=0
```

ผลก่อนแก้ ผลหลังแก้ คำตอบดิบ ข้อเสนอที่ถูกปฏิเสธ รีวิว และหลักฐานการเขียนอยู่ใน [receipt และรายการไฟล์](../evidence/2026-10-26/h1b-live/receipt.json) โค้ดจริงอยู่ที่ [จุดบันทึกผล](../../internal/skills/behavioral.go) และ [ตัวอ่านหลักฐาน](../../internal/skills/behavioral_paired.go)

## ข้อจำกัดที่พบจากการใช้โมเดลจริง

งานที่ส่งรวมหลายส่วนชนเพดานคำตอบ 3072 tokens การแยกงานทำให้ได้ข้อเสนอที่ครบ แต่โมเดลยังจับข้อความเดิมสำหรับแก้ไฟล์ CRLF ไม่แม่น สร้างวงเล็บปิดผิด และเขียนเงื่อนไขทดสอบที่มอง error ที่คาดไว้เป็นข้อผิดพลาด ต้องอ่านผลจาก compiler และส่งงานซ่อมแบบเจาะจงกลับหลายครั้ง ข้อเสนอที่ผิดไม่เคยถูกนำเข้าไฟล์จริง

ข้อเสนอแบบไฟล์ใหม่และไฟล์ฉบับเต็มภายใต้ขอบเขตเล็กผ่านการตรวจได้ ส่วนทดสอบขอบเขตสำเร็จเมื่อแยกกรณีที่ต้องมี error ออกจากกรณีที่ต้องไม่มี error การสั่งงานจึงควรแนบ helper และ schema จริง ตรึงเงื่อนไขยืนยันผล และตรวจทั้งไวยากรณ์กับความหมายก่อนรีวิว

ผู้ควบคุมมีส่วนทำให้บางครั้งล้มเหลวด้วย ตัวเรียกงานช่วงแรกข้าม preset/provider service และบาง packet ไม่ได้แนบ signature ของ helper หรือชื่อฟิลด์ครบ ข้อผิดพลาดเหล่านี้ถูกแก้ที่การจัดงาน ไม่ควรนับเป็นบั๊กผลิตภัณฑ์ทั้งหมด สถานะ heartbeat ระหว่างรอโมเดลก็ไม่ใช่การ retry

รีวิวครั้งแรกเข้าใจผลที่ตั้งใจให้ตกก่อนแก้เป็นผลหลังแก้ และสับสนจำนวนแถวในตารางทดสอบกับจำนวนไฟล์ การแยกป้ายหลักฐานก่อน/หลังและแนบ helper ฐานข้อมูลแก้ความกำกวมนี้ได้ โดยไม่แก้ source เพื่อเอาใจ reviewer ทั้งสองคำตัดสินถูกเก็บไว้ โมเดลที่ใช้รีวิวเป็นตัวเดิม จึงยังไม่มีหลักฐานจากโมเดลต่างตระกูล

## งานที่ต้องทำต่อ

1. H1A ต้องมี evaluation run ที่ตรึง candidate/base version และ hash ตั้งแต่ก่อนรัน พร้อม provider/evaluator/environment/dataset identity ผลล่าช้าหรือผลที่ส่งซ้ำต้องใช้กับรุ่นใหม่ไม่ได้
2. H1B ส่วนที่เหลือต้องรับผลตาม case manifest ที่ host ตรึงไว้ คำนวณ false success จากหลักฐาน ตรวจกรณีที่หายหรือเกิน และปิดช่องเลื่อน Skill ด้วยยอดรวมที่ไม่มีที่มา รวมถึงจัดการผลเก่าที่บันทึกไว้
3. H1C ต้องผูก direct skill_manage กับ project/session และเจ้าของจริง เช่นเดียวกับ background learning พร้อมทดสอบการแยก project และการข้าม scope
4. H2 ถึง H8 และ marketplace M0 ถึง M10 ยังอยู่ในขอบเขตเดิมตาม [execution contract](../redesign/2026-10-25-hermetrix-marketplace-execution-contract.md)

โมเดล Bonsai ที่ 8088 ทำงานจริงแล้ว และการตรวจ hostile fixtures ผ่าน 24/24 แต่ยังไม่มีหลักฐานรับรอง UX/UI, งาน Goal แบบอัตโนมัติครบวงจร, การควบคุมเครื่อง, marketplace, Compose หรือ Kubernetes จากผลครั้งนี้

ระบบตรวจอนุมัติอัตโนมัติปฏิเสธการเปิด serving harness ที่ 18816 ก่อนคำสั่งเริ่มทำงาน โดยแจ้งเพียง “blocked by policy” ไม่มีเหตุผลละเอียด จึงไม่ได้เปิดเซิร์ฟเวอร์หรือเปลี่ยนเส้นทางเพื่อหลบข้อจำกัด การทดสอบครั้งนี้เรียกโมดูลเดิมแบบไม่มีเซิร์ฟเวอร์ และใช้สำเนาฐานข้อมูลแยกจากข้อมูลติดตั้งจริง
