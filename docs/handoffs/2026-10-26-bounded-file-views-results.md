# ผลตรวจส่วนพื้นฐานของ bounded file views

วันที่ 26 ตุลาคม 2026

Hermetrix เขียนตัวสร้างและตรวจข้อมูลส่วนไฟล์ พร้อมชุดทดสอบ แล้วนำเข้า workspace ผ่าน WriteProjectFilesAtRoot จริง 7 ไฟล์ ได้แก่ production helper 1 ไฟล์และ tests 6 ไฟล์ มี mutation receipts ครบ ไม่เกิด rollback และไฟล์ตรงกับฉบับที่ผ่านรีวิว การทดสอบจากไฟล์จริงและ build ผ่านแล้ว

นี่คือ H1D ขั้น A1 ตาม [สัญญางาน](2026-10-26-bounded-file-views-contract.md) ยังไม่มีการเชื่อม Task หรือ transport เมื่อส่งไฟล์ agent/service.go ขนาด 172,056 bytes ระบบยังปฏิเสธก่อนเรียก provider ด้วยเพดาน 128 KiB ตามเดิม จึงยังไม่ถือว่าแก้ไฟล์ใหญ่ครบวงจรได้

## พฤติกรรมที่ตรวจได้

BoundedFileView ผูก path แบบ relative ที่เป็น canonical กับ SHA ของ source เต็ม ช่วง byte เนื้อหา และ RegionID ที่คำนวณซ้ำได้ ตัวตรวจรับ expected path, source และ hash แยกจาก view ปฏิเสธข้อมูลที่ไม่ตรงกัน ตำแหน่งผิด UTF8/CRLF และ path ที่ข้ามขอบเขต ไฟล์ว่างจริงผ่านได้ แต่ marker absent ผ่านไม่ได้

helper ไม่มี filesystem, network, DB หรือสิทธิ์เขียนไฟล์ RegionID เป็นตัวระบุข้อมูล ไม่ใช่สิทธิ์อนุญาต ขั้น A3 ยังต้องให้ host ตรึงขอบเขตใน Task และห้ามคำตอบโมเดลกำหนดสิทธิ์ให้ตัวเอง

| การตรวจ | ผล |
| --- | --- |
| ฟังก์ชันทดสอบเฉพาะ A1 | ผ่าน 8 ฟังก์ชัน |
| ตารางทุกคู่ตำแหน่งของ fixture | ผ่าน 15 คู่ที่ถูกต้อง และปฏิเสธ 66 คู่ที่ผิด |
| path | รับ nested/dotfile/Unicode และปฏิเสธ 13 กรณีที่ผิด |
| hash และ source | ปฏิเสธ hash ผิด 5 แบบ และ source ที่ไม่ใช่ UTF8 |
| view และ snapshot | ปฏิเสธการเปลี่ยนแต่ละ field, expected path ที่ไม่ตรง และ source เต็มที่เปลี่ยนแม้เนื้อหาส่วนที่เห็นยังเหมือนเดิม |
| ชุดทดสอบเดิมบนข้อเสนอ | worker และ taskcoord ผ่าน |
| ไฟล์จริงหลังนำเข้า | worker และ skills ผ่าน; build cmd/hermetrix และ go vet ของสอง package ผ่าน |
| รีวิว | อนุมัติ ไม่มี finding ค้าง ใช้โมเดลเดิมแยกอีกครั้ง |
| Native apply | receipts 7 รายการ, rollback 0 |
| SHA ของสองชุดงานรวมกัน | H1B 9 ไฟล์ และ A1 7 ไฟล์ ตรงกับฉบับรีวิวครบ 16 ไฟล์ |

กลุ่มกรณีบางส่วนซ้ำกัน จึงไม่นำจำนวนในแต่ละกลุ่มมาบวกเป็นจำนวนงานที่ไม่ซ้ำ หลักฐานทั้งหมดอยู่ใน [receipt](../evidence/2026-10-26/h1d-live/receipt.json) และ [โค้ดจริง](../../internal/worker/file_views.go)

## ข้อผิดพลาดและการแก้ที่มีหลักฐาน

ข้อเสนอช่วงแรกคอมไพล์ไม่ผ่าน และหลังแก้ให้คอมไพล์ได้ยังปฏิเสธไฟล์ปกติ จากนั้นผ่านกรณีพื้นฐานแต่ยอมรับ ../x.go และตำแหน่งที่ตัด CRLF การแก้ด้วยการอ่านไบต์โดยตรงยังเกิด panic ที่ช่วงว่าง 0 ถึง 0 จึงหยุดวิธีเดิมและเปลี่ยนเป็นตรวจ prefix/suffix ด้วยฟังก์ชันมาตรฐาน โดยไม่เปลี่ยน source ต้นฉบับ วิธีนี้ผ่านตาราง 81 คู่ครบ รวมช่วงว่างท้ายไฟล์และคู่ CRLF ที่อยู่ครบทั้งคู่

ชุดทดสอบที่โมเดลสร้างก็มีข้อผิดพลาด ทั้งใช้ raw string แทน CRLF จริง เลือก path ที่ผิดจนกลบเหตุที่ต้องตรวจ ใช้ข้อมูล byte กับ API ที่รับ string และเปลี่ยน source ในกรณีที่ต้องเปลี่ยนเพียง hash ผู้ควบคุมจึงตรึงข้อมูลตั้งต้นเป็นลำดับไบต์และค่า hash แล้วให้ Hermetrix แก้ตัวทดสอบก่อน ไม่แก้ implementation ให้ผ่านบททดสอบที่ผิด

การจัด packet มีส่วนด้วย บางรอบไม่ได้แนบ symbol ที่ใช้ เช่น Hash และจำนวนค่าที่ constructor คืน ทำให้เกิดการเดา API การจัดงานถัดไปต้องแนบ declaration จริงของทุก API ที่เกี่ยวข้องทั้งตอนเขียนและตอนซ่อม การผ่าน schema ของคำตอบหรือคำว่า approve จากโมเดลยังต้องตรวจเทียบกับ compiler, fixtures และจำนวนไฟล์จริง

## ผลทดลอง preset ภายในงบเดิม

ใช้โมเดลเดิมและ repair task เดียวกันหนึ่งคู่ เปรียบเทียบ preset เดิมกับสำเนาที่ให้ reasoning 1024 tokens และ answer reserve 2048 tokens ภายใต้ generation cap 3072 เท่ากัน สำเนาอยู่ใน audit DB แยก ไม่เปลี่ยนการตั้งค่าติดตั้งจริง

| การตั้งค่า | ผลรอบนั้น |
| --- | --- |
| reasoning disabled | ได้ข้อเสนอครบ ใช้ completion 1382 tokens ผ่านสองกรณีพื้นฐาน แต่การตรวจภายหลังยังพบ traversal และ CRLF จึงไม่รับ source รุ่นนั้นทันที |
| bounded reasoning 1024 | ใช้ completion 3072 tokens แล้วจบด้วย length ไม่มีข้อเสนอครบที่รับไป apply ได้ |

จึงไม่รับ preset ทดลองนี้เป็นค่าใช้งานจากผลรอบเดียว ไม่ได้สรุปว่า reasoning หรือโมเดลอื่นด้อยกว่าโดยทั่วไป source ที่ผ่าน A1 เกิดจากงานซ่อมเพิ่มเติมพร้อมหลักฐาน ไม่ใช่ผลของ preset ทดลองที่ล้มเหลว ดู [บันทึกการทดลอง](../evidence/2026-10-26/h1d-live/H1D-A1-reasoning-experiment.json)

## งานถัดไป

A2 นำเข้าผ่าน native API พร้อมผลตรวจจริงแล้ว ดู [ผล A2](2026-10-26-bounded-edits-results.md) ขั้นถัดไปคือ A3 และ B ให้ Task, wire payload, persisted-result validation, coordinator, apply และ review ใช้ข้อมูลส่วนไฟล์โดยยังผูกกับ snapshot เต็ม แล้วพิสูจน์กับโมเดลจริงบน fixture เกิน 128 KiB

H1A การผูกผลประเมินกับรันที่เริ่มจริง, H1B ส่วน provenance/promotion, H1C ขอบเขต Skill ตลอดจน UX/UI, computer control และ marketplace ตาม execution contract ยังอยู่ในเป้าหมายเดิมทั้งหมด
