# Hermetrix workflow and interface reliability plan

Date: 2026-09-28

Status: In progress; user authorized implementation with live verification after each slice.

## Outcome and scope

Make Chat, Workspace, Agent Team, Tasks, Browser, Models, Tools, Skills, MCP, and Settings understandable and usable in a real workflow. Preserve Hermetrix's local-first controls, frozen Session Contracts, reviewable Skills, durable Task evidence, and explicit approval for effects. Codex is a reference for the clarity of navigation, reading, settings, and browser interaction, not a requirement to copy its internal architecture or branding.

Work only against isolated project fixtures and cloned/new application data until a slice has passed. The existing working tree contains extensive user changes; keep those changes intact. Do not treat a green build as proof that a person can complete the journey.

## แผนลงมือฉบับครบ — 2026-09-29

ส่วนนี้เป็นรายการงานหลักสำหรับการทำต่อจากสถานะปัจจุบัน ส่วน `Baseline evidence` และ `Implementation and live receipts` ด้านล่างเป็นบันทึกผลตรวจตามเวลา ไม่ใช่คำยืนยันว่าหัวข้อนั้นเสร็จแล้ว แผนนี้ครอบคลุมการใช้งานและหน้าตา Hermetrix ที่ผู้ใช้ระบุ รวมทั้งความถูกต้องของ Main/Worker, Bonsai 64k, provider, Tools/Skills/MCP และการตรวจผลจริง งาน social publishing, media production และ native Windows automation ในแผน Goal-Driven Workbench อีกฉบับไม่ใช่เงื่อนไขของงานปรับ UI ชุดนี้ แต่จุดเข้าถึงและสถานะของความสามารถเหล่านั้นใน Settings/Workspace ต้องไม่เสีย

### ผลลัพธ์และโครงหน้าจอที่ต้องได้

1. ทางเข้าหลักมี **Chat, Workspace, Tasks, Browser, Settings** พร้อมรายการ Project/Session ที่รู้ว่ากำลังทำงานใดอยู่; ไม่ต้องเดาว่าปุ่มหลายตำแหน่งทำสิ่งเดียวกันหรือไม่
2. Chat เป็นจุดเริ่มงานสนทนา ส่วน Workspace เป็นพื้นที่เดียวกันเมื่อมีไฟล์/Browser/หลักฐาน; conversation และ composer ผูก session เดียว และ Review เปิดดูจากผลลัพธ์ได้ ไม่บังคับเปิดหลาย panel ก่อนเริ่ม
3. Settings จัดเป็น **Models**, **Capabilities (Tools/Skills/MCP)**, **Projects & permissions**, **Appearance & language**, **Advanced diagnostics/system**; รายการเดิมทุกหน้า (MCP server, built-in tools, Skill Studio, Proposals, Learning, Insights, Archive, Context, Fidelity, Discord remote, Projects, Background jobs, Artifacts, Maintenance) ต้องมีปลายทางใหม่/deep link ที่ใช้ได้และข้อมูลไม่หาย
4. สิ่งสำคัญบนหน้าจอแสดงเป็น `สถานะ → เหตุผล → สิ่งที่ทำได้ต่อ`; log, ID, hash, usage และ receipt เปิดจาก Details ได้ บอกแหล่งวัดและเวลาเสมอ
5. การเลือก provider มี **ค่าเริ่มต้นสำหรับงานใหม่หนึ่งค่า** ซึ่งกำหนดจาก Models; selector ใน Chat/Workspace/Team/Task/reviewer อ่าน registry เดียวกัน แต่ยังเลือกต่างจากค่าเริ่มต้นได้เมื่อกำหนดงาน Session ที่เริ่มแล้วใช้ contract เดิมจนกว่าจะสร้าง session ใหม่

### ชุดทดสอบการใช้งานจริงที่ห้ามข้าม

1. **Provider retention:** ก่อน/หลัง migration และ restart ตรวจ ID, model, endpoint, local/remote, credential presence ของ Qwen และ Bonsai โดยไม่พิมพ์ secret; ทดสอบ key ขาด/ปลายทาง offline/ทดสอบสำเร็จแยกสถานะ
2. **Coding journey เดียวกันหลายทาง:** Fixture มีหลายไฟล์และ test ที่เริ่มจาก fail แล้ว pass; ทำผ่าน Chat, Workspace, Team และ durable Task; ตรวจว่า Main ใช้ผลงาน Worker จริง ไม่เพียงกล่าวว่าได้ตรวจ
3. **Negative Task:** บังคับ check fail, denial, reviewer unavailable, stale revision และ restart กลาง effect; ตรวจ rollback/no replay/next action
4. **Capability journey:** built-in tool หนึ่งตัว, Skill แบบ versioned หนึ่งตัว, MCP ชื่อซ้ำจากสอง server; ตรวจ discover → activate/connect → approval → execute → receipt และ denied/recovery
5. **Browser journey:** หน้า fixture ที่คลิก/พิมพ์/scroll แล้ว DOM เปลี่ยน; ทำโดยผู้ใช้และ agent แยกกัน รวม keyboard, mobile, pane switch และ restart
6. **Bonsai 64k:** วัด runtime allocation/fingerprint, ทดสอบข้อมูลยาวใกล้เพดานที่มี marker กระจายต้น/กลาง/ท้าย, เทียบคำตอบกับ ground truth, บันทึก provider input tokens, omissions, latency, memory/resource และ Main/Worker handoff; ถ้า runtime/model ไม่รองรับให้ลด profile ตามหลักฐานและแจ้งเหตุ
7. **Visual/setting matrix:** Chat, Workspace, Task, Browser, Models, Capabilities และ Settings ทุกหน้าที่มีอยู่ ที่ desktop/tablet/390px; mouse/touch/keyboard, Thai/English, fresh/empty/loading/error/offline/stale/complete

### เกณฑ์จบงานทั้งแผน

- ทุกข้อ U01–U13 มีผล **ผ่าน** จากแอปที่รันจริง, หลักฐานคำสั่ง/API/receipt และ screenshot ในกรณี UI; `ยังไม่ตรวจ` หรือ `ผ่านเฉพาะ test` ไม่นับว่าผ่าน
- ไม่มี provider ที่เคยเพิ่มถูกลบหรือแทนที่โดยเงียบ และไม่แสดง key ในหน้า/บันทึก; installed user data ยังไม่ถูกใช้เป็น fixture
- Main/Worker/Task/Skill/MCP/Browser ครบทั้ง success และ failure/recovery ที่ระบุ; reviewer กับ 64k กล่าวอ้างตามระดับหลักฐานที่ตรวจได้เท่านั้น
- focused tests และ full Node/Go/browser regression ผ่านหลังแก้ความล้มเหลวจากต้นเหตุ; migration/restart ไม่ทำข้อมูลหรือ approval หาย
- ส่งมอบรายการสิ่งที่เปลี่ยน วิธีใช้ใหม่ ภาพก่อน/หลัง ผลทดสอบและข้อจำกัดที่เหลือ ก่อนนำ preview ไปใช้แทนแอปที่ติดตั้ง

The 9arm credential was cleared from the isolated preview after the audit; the profile was not deleted. Treat credential presence and live connectivity as separate states from profile registration.

## Product rules

1. One provider registry is authoritative. Every Chat, Workspace, Team, Task, and reviewer picker reads its readiness and model metadata from that registry. A selection shows the exact provider, model, local/remote route, usable context evidence, and the effect of changing it.
2. Session creation and Team child creation use the same remote-egress decision. Approval is explicit and frozen into each child contract; the UI must show it before dispatch. Qualification and egress are separate decisions.
3. The primary UI says what happened and the next useful action. IDs, hashes, token counts, receipts, and raw errors remain reachable in details.
4. Tools, Skills, and MCP share one discovery surface with source, scope, readiness, risk, and an actionable test/usage path. Distinct servers cannot look like one capability.
5. Browser must let the user navigate, click, type, inspect, and recover within the pane where those actions are supported, while agent actions retain fresh-observation and approval gates.
6. A Task check is frozen only after preflight confirms that its executable and prerequisites exist for the selected project. A failing check points to the failed requirement and a recovery action.
7. A reviewer profile alone does not prove independence. Display and enforce the actual review policy using provider/model/endpoint identity, with an explicit same-model limitation where allowed.
8. Preserve existing provider profiles and user configuration while redesigning Models. Migrate rather than recreate records; never silently delete a profile, replace its endpoint, or clear a credential as a side effect of UI work. Show credential presence without revealing the secret.

## Complete change inventory and priority

Priority means order of implementation, not a claim that an existing feature is broken. Each row needs a visible acceptance run in the application, in addition to focused tests. Keep capabilities unique to Hermetrix where they help the user finish work; simplify the path to them.
