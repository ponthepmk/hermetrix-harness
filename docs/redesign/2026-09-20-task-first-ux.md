# Hermetrix: เริ่มจากเป้าหมายและตรวจผลก่อนปิดงาน

ปรับปรุงวันที่ 20 กันยายน 2026 ตามการทดลองใช้งานบน Windows

## ปัญหาที่ตรวจพบ

- หน้าแรกไม่มีช่องเริ่มงาน แต่แสดงว่าเชื่อมโมเดลสำเร็จทั้งที่ provider แรกไม่มี credential
- เปิด Files, Code และ Terminal พร้อมกัน ทำให้พื้นที่คุยเล็กลง และ Terminal บน Windows build นี้เปิดไม่ได้
- หน้า Chat รอข้อมูล 21 endpoint รวมหน้าตั้งค่าที่ผู้ใช้ยังไม่ได้เปิด และโหลด IDE bundle ประมาณ 1 MB ทันที
- หน้าวางแผนไม่ส่ง run authority ไปยัง API ที่จำเป็น จึงไปต่อถึงการเสนอ/ใช้/ตรวจโค้ดไม่ได้
- ไม่มีปุ่มทำขั้นต่อไปหลังขั้นแรกผ่าน และตัวเลือก reviewer ไม่ตรวจเงื่อนไขอิสระครบ

## โครงสร้างที่ใช้

1. เลือกโปรเจกต์ → พิมพ์เป้าหมายที่หน้าเริ่มงาน
2. **เริ่มคุย** สร้าง session และส่งโจทย์ในครั้งเดียว ตั้งชื่อจากเนื้อหางาน
3. **วางแผนงาน / Plans** ย้ายโจทย์ไปหน้าแผนเต็มพื้นที่ เพิ่มผลลัพธ์ที่ใช้ตรวจรับได้
4. สร้างแผน → อ่านขั้นตอน ขอบเขต และคำสั่งตรวจ → สร้างข้อเสนอทีละขั้น
5. อ่านเนื้อหาไฟล์ในข้อเสนอ → อนุมัติ → ใช้การเปลี่ยนแปลง → รันรายการตรวจ → ให้ reviewer อิสระตรวจ
6. เมื่อขั้นหนึ่งผ่าน แสดงปุ่มเริ่มขั้นถัดไป; งานจะเสร็จเมื่อ backend ยืนยันหลักฐานครบ

การตั้งค่าโมเดลเปิดเป็น dialog จากปุ่มชื่อโมเดลหรือ “โมเดลและตัวเลือก” ใน sidebar ส่วนเครื่องมือและไฟล์เปิดตามต้องการ การเพิ่ม Skill ไม่ใช่เงื่อนไขเริ่มคุย

## พฤติกรรมสำคัญ

- เลือก provider ที่ enabled และ credential_ready ก่อน เมื่อผู้ใช้เลือกเองให้เคารพตัวเลือกนั้น
- แสดงสถานะพร้อมเริ่มและสาเหตุที่เริ่มไม่ได้ ไม่ใช้จำนวน session ของโปรเจกต์อื่นเป็นหลักฐาน onboarding
- แยก layout ของ Chat และ Workspace ต่อโปรเจกต์ ด้วย storage v3; layout รุ่นเก่าเริ่มด้วยค่าใหม่ครั้งแรก
- Chat เริ่มด้วยพื้นที่ทำงานด้านข้างปิด; Workspace เริ่ม Files + Code ไม่เริ่ม Terminal เอง
- ใช้ runtime capability ของ server เพื่อแสดงข้อจำกัด Terminal และป้องกันคำขอที่ทำไม่ได้
- Plan ใช้ local-only ตามนโยบายเดิม ไม่เพิ่มสิทธิ์ส่งข้อมูลออกโดยอัตโนมัติ
- แสดงข้อเสนอ immutable ก่อนอนุมัติ; ส่ง run ID และ lease token ครบใน protected actions
- ต่อ lease ขณะเปิดงานและก่อนลงมือ พร้อมป้องกันกดซ้ำและการทำงานหลัง lease หมดอายุ
- Reviewer ต้องมี credential พร้อม และเป็นคนละโมเดลหรือ endpoint จาก implementer
- ถ้ายังมีโมเดลพร้อมใช้เพียงตัวเดียว แสดงข้อจำกัด reviewer ก่อนเริ่มงาน ไม่ปล่อยให้รู้ตอนตรวจขั้นสุดท้าย
- ข้อผิดพลาดในแผนคงอยู่บนหน้า จนผู้ใช้ลองขั้นนั้นใหม่ ไม่หายไปพร้อม toast
- แสดงแผนเป็นข้อเสนอ ความเป็นไปได้พิสูจน์ด้วยผลตรวจจริง ไม่ถือว่ามีแผนเท่ากับงานทำสำเร็จ

### แก้ blocker ที่พบจากโมเดลจริง

Bonsai ที่ตั้ง context 61,440 tokens เริ่ม planner ไม่ได้ เพราะ preset เดิมจอง input สูงสุด 60,000 พร้อม output 5,120 และ safety 512 ซึ่งรวมเกิน context แม้ prompt จริงจะสั้น การแก้ไขสร้าง preset อนุพันธ์แบบ immutable ที่ลดเฉพาะเพดาน input เหลือ 55,808 โดยรักษา output/reasoning reserve ไว้ บันทึก ID/revision เดียวกันใน artifact และ ledger และตรวจขนาด input จริงก่อนส่งเสมอ ไม่แก้ค่าความจุโมเดลให้สูงกว่าความจริง

การทดสอบถัดมาพบว่า preset มีงบ reasoning แต่ adapter ไม่ส่งไปยังโมเดล จึงสร้างแผนไม่จบก่อนเต็ม 5,120 tokens การแก้ไขส่ง `reasoning_budget_tokens: 3072` และ `reasoning_format: deepseek` เฉพาะ local llama.cpp ที่ตรวจ `/props` ว่าเป็น build ที่รองรับ พร้อม cache และ timeout ไม่มีการเพิ่มเพดาน output หรือส่งพารามิเตอร์เฉพาะนี้ให้ remote/unknown runtime แหล่งยืนยันคือ [source ของ llama.cpp commit ที่เครื่องนี้รัน](https://github.com/ggml-org/llama.cpp/blob/9a9394a89/tools/server/server-common.cpp#L1260)

## การลดงานที่หน้าเว็บทำ

- เส้นทางเปิด Chat โหลดข้อมูลหลัก 4 endpoint แทนชุดเดิม 21 endpoint (ไม่นับรายการโปรเจกต์ก่อนเปิดและรายละเอียด session ที่เลือก)
- โหลดข้อมูลและ render หน้าตั้งค่าเมื่อเปิดใช้งาน
- โหลด IDE JavaScript/CSS เมื่อเปิดไฟล์หรือ Terminal ที่ใช้ได้ ด้วย promise เดียวป้องกันโหลดซ้ำ
- แยก timer ของ Terminal และ Team; หยุด poll เมื่อหน้าถูกซ่อนหรือ pane มองไม่เห็น
- Terminal ที่ไม่มี output ลดความถี่จาก 160 ms เป็น 800 ms
- Pane ที่ซ่อนจากการขยาย pane อื่นไม่ mount editor/terminal
- ยกเลิกผลโหลดที่ล้าสมัยเมื่อสลับโปรเจกต์ ป้องกันไฟล์หรือหน้าตั้งค่าของโปรเจกต์เดิมทับหน้าปัจจุบัน
- ความล้มเหลวของข้อมูลประกอบไม่ทำให้ Chat ทั้งหน้าหายไป และไม่ render ฟอร์มตั้งค่าซ้ำหลังเริ่มกรอก

ตัวเลขนี้เป็นปริมาณงานจาก implementation และ browser assertions ไม่ใช่ผล benchmark ความเร็วโมเดลหรือเวลาตอบของงานทุกชนิด

## การตรวจรับ

- Browser จริง: เริ่มจากโจทย์ → เลือกโมเดลที่พร้อม → รับ streaming reply → ตรวจ session ที่บันทึกถูกโปรเจกต์
- Browser จริง: เปลี่ยนโจทย์เป็นแผน → เก็บข้อความเดิม → บังคับกรอกเกณฑ์สำเร็จ → บันทึก task แบบ local-only
- Browser จริง: ไม่มี request สำหรับ IDE และหน้าตั้งค่าที่ซ่อนบนหน้าเริ่มต้น
- Browser จริง: เปิดไฟล์และบันทึกได้; Windows แสดง Terminal unavailable โดยไม่ส่งคำขอเริ่ม Terminal
- Node: authority, renewal, packet revision, ขั้นถัดไป, provider/reviewer, expired/uncertain state, proposal escaping และ heartbeat เปลี่ยน DOM
- Backend: ชุดทดสอบ taskengine, taskcoord และ web
- Web suite ล่าสุด: 57 tests ผ่าน ไม่มี skip รวม Chrome tests 3 เส้นทาง
- Node: 26 tests ผ่าน ครอบคลุมการโหลดข้อมูลช้า สลับโปรเจกต์ และแผนหลายขั้น
- `go test ./...` และ `go vet ./...` ผ่าน รวมการตรวจซ้ำหลังปรับ reasoning transport
- โมเดลจริงในโปรเจกต์ทดลอง: แชทภาษาไทยตอบกลับได้ และสร้างแผนหนึ่งขั้นสำหรับ HELLO.md สำเร็จ มีเกณฑ์ AC-1 และคำสั่งตรวจด้วย Node; task อยู่ในสถานะ ready โดยไม่แก้ไฟล์โปรเจกต์ของผู้ใช้
- ผลโมเดลจริงนี้ยืนยันถึงการสร้างแผน ยังไม่ได้ยืนยันการ apply/check/independent review ครบวงจรกับโมเดลจริง ชุดทดสอบอัตโนมัติใช้ fixture สำหรับขั้นเหล่านั้น

## ข้อจำกัดและลำดับถัดไป

1. **Reviewer บนเครื่องจริง:** ต้องตั้งค่าโมเดลหรือ endpoint อิสระตัวที่สอง จึงพิสูจน์วงจรตรวจงานครบกับโมเดลจริงได้ ห้ามเพิ่ม provider ชื่อใหม่แต่ชี้โมเดล/endpoint เดิมเพื่อหลบกฎ
2. **แผนที่โมเดลสร้าง:** planner รับ bounded secret-filtered repo manifest และ exact executable allowlist แล้ว คำสั่งยังต้องพิสูจน์ด้วยการรันจริง ไม่มีการรับประกันว่าแผนใด ๆ ใช้ได้เพียงเพราะ schema ผ่าน
3. **กู้ run ที่หมดอายุหลังใช้โค้ด:** backend/UI มี explicit recovery แล้ว; planned effect ถูก abandon และถ้าทุก effect มี receipt ระบบหมุน lease generation แล้วทำ attempt เดิมต่อได้ หากมี dispatched effect ที่ยังไม่มี receipt จะเปลี่ยนเป็น uncertain และ pause เพื่อ reconcile โดยไม่ replay
4. **Windows interactive terminal:** ใช้ PowerShell/cmd ผ่าน ConPTY จริง รองรับ input, resize, Ctrl+C, close และ process-tree cleanup; command runner ยังมีเพียง Job Object containment ไม่ใช่ filesystem/network sandbox
5. **ข้อมูลจำนวนมาก:** pagination ของ sessions/events, incremental transcript rendering และ benchmarking กับประวัติยาวยังเป็นงานต่อยอด

การปรับชุดนี้ไม่เปลี่ยนกฎอนุมัติ การคุ้มครองข้อมูลออกนอกเครื่อง หรืออำนาจการใช้เครื่องมือ

## ตรวจ layout และ action flow เพิ่มเติม

รอบนี้ใช้การกดผ่าน Chrome จริงที่ 1280×720, 800×900 และ 390×844 พร้อมตรวจไฟล์บนดิสก์หลังบันทึก แยก fixture ออกจากโปรเจกต์ที่ผู้ใช้ทำงานอยู่

### ปัญหาที่ทำซ้ำได้และพฤติกรรมที่แก้ไข

- ชื่อโปรเจกต์บนจอแคบสูงเกิน header และถูกตัด: เปลี่ยนเป็น header สองแถว แถวแรกเลือกโปรเจกต์/เปิด sidebar/ตั้งค่า แถวที่สอง Chat, Plans, Workspace ชื่อยาวตัดด้วย ellipsis
- ปุ่ม Save/Review ล้นออกนอกหน้าจอ: toolbar ขึ้นบรรทัดใหม่ได้ และหน้าจอไม่เกิน 700 px แสดง Workspace ทีละ pane พร้อมแท็บ Files/Code/เนื้อหาอื่น เปิดไฟล์แล้วแสดง editor ทันที
- เข้า Plans แล้วกลับ Workspace เหลือ Tasks เป็นช่องที่สาม: เก็บการจัดวางเดิมก่อนเปิด Plans ชั่วคราว และคืนค่าเมื่อกลับ ไม่บันทึกหน้าวางแผนทับ layout ของ Workspace
- ตัวแก้ไขโค้ดแสดงเลขบรรทัดเหนือข้อความและโค้ดถูกตัด: สไตล์ที่ CodeMirror สร้างขณะทำงานถูก CSP บล็อก จึงเพิ่ม nonce ของสไตล์เฉพาะ HTML แต่ละ response พร้อม no-store แล้วให้ editor ใช้ nonce เดียวกัน ไม่เพิ่ม unsafe-inline และคงนโยบาย scripts/artifacts เดิม ทดสอบตำแหน่ง code/gutter ที่มองเห็นจริง
- ปุ่ม Files ใน Chat เปิด side pane ที่ CSS ซ่อนบนจอไม่เกิน 920 px: เปลี่ยนไปเปิดใน Workspace หลัก ข้อความร่างยังอยู่เมื่อกลับ Chat
- ปุ่มโมเดลเดิมเปิดตัวเลือกสองชั้นใน sidebar: เปลี่ยนเป็น native dialog พร้อมชื่อที่ screen reader อ่านได้ รองรับ Escape และคืน focus ไปยังปุ่มเปิด ตัวเลือกขั้นสูงพับไว้ โมเดลที่เลือกคงอยู่เมื่อปิด/เปิด dialog
- ตัวเลือกโปรเจกต์ซ้ำในแบบฟอร์มเริ่มแชททำให้ workspace กับ session คนละโปรเจกต์: session ใหม่ผูกกับโปรเจกต์ที่เปิดอยู่ เปลี่ยนโปรเจกต์จาก navigation กลาง
- กด session ของอีกโปรเจกต์แล้ว Files/Plans ยังอยู่โปรเจกต์เดิม: โหลดเจ้าของ session ให้ตรงก่อนแสดง พร้อมป้องกันผลโหลดเก่าทับการเลือกใหม่
- ข้อความและรูปแนบร่างใช้ state ร่วมกัน: แยกตาม session; เป้าหมายและเกณฑ์แผนแยกตาม project เก็บร่างก่อนเปลี่ยนหน้า ข้อมูลร่างนี้อยู่ในหน่วยความจำและไม่รับประกันหลัง reload/ปิดแอป
- ส่งข้อความไม่สำเร็จแล้วช่องพิมพ์ว่าง: คืนข้อความและรูปแนบในช่องที่ผู้ใช้เห็น หลังส่งสำเร็จล้างรูปที่ส่งแล้ว
- สลับ session ระหว่างอัปโหลดรูปหลายไฟล์ทำให้ไฟล์ถัดไปใช้เจ้าของใหม่: ผูก upload กับ project/session ตอนเริ่ม และหยุดคิวที่เหลือหากผู้ใช้เปลี่ยนงาน
- กด Plans แล้วเปลี่ยนหน้าในช่วงที่ข้อมูลยังโหลด: ผลโหลดช้าไม่ดึงผู้ใช้กลับหน้า Plans; การ refresh transcript เบื้องหลังไม่ถือเป็นคำสั่งเปลี่ยนหน้า
- การสร้าง session กำลังรอคำตอบ: ป้องกันการสลับเจ้าของงานจนสร้างและเลือก session เสร็จ หากล้มเหลวปลดล็อกและเก็บโจทย์เดิม
- ปุ่ม Format/Run/Test/Debug บน Windows ใช้ interactive terminal ที่ยังไม่รองรับ: ปิดปุ่มพร้อมอธิบายเหตุผล Save และ Review ยังใช้ได้ตามปกติ

### เกณฑ์ตรวจรับของรอบนี้

1. ปุ่มใน header อยู่ภายในหน้าจอ และ Save กดด้วย pointer แล้วไฟล์บนดิสก์เปลี่ยนจริง
2. เปิดตัวเลือกโมเดล เปลี่ยนค่า ปิดและเปิดใหม่ ค่าไม่หาย และเป้าหมายที่พิมพ์ไว้ไม่หาย
3. สลับ Chat → Plans → Chat และ Code → Chat → Code แล้วร่างที่เกี่ยวข้องยังอยู่
4. ผลโหลด session เก่าและคำขอเปลี่ยนหน้าที่หมดอายุไม่เปลี่ยนงานปัจจุบัน
5. เปิดแชทต่างโปรเจกต์แล้วชื่อโปรเจกต์ Files และแผนอยู่ภายใต้เจ้าของเดียวกัน
6. ไม่แสดงปุ่มที่ดูพร้อมทำงานหาก capability ของ runtime ยืนยันว่าใช้ไม่ได้
