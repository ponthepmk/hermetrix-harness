## Defects and changes

1. **New project cannot produce new source files through Task.** `internal/taskcoord/service.go` rejects an empty source manifest and reads only existing selected files. `internal/product/workbench.go` batch writes also require existing preimages. This is a functional blocker for a normal “create a project” request; creating placeholders is a test workaround, not a product solution.
2. **Windows new-file error wording was not recognized.** Updated `internal/web/ui/app.js` to treat `cannot find the file/path` as an absent new-file case. Verified by creating and saving `PLAN.md` in Files.
3. **Plans showed unrelated content publishing tools for a CMS development task.** Grouped research and publishing tools into a collapsed optional disclosure and removed a duplicated goal paragraph from the primary task surface. The staging browser now shows the collapsed disclosure below the task evidence and above the next action.
4. **Slow local reviewer timed out and restart offered an unusable review action.** `internal/providers/openai.go` now grants the default local HTTP client 30 minutes, while remote and explicitly configured clients retain their timeout. `internal/taskengine/execution.go` adds a narrowly scoped review recovery that requires terminal effect receipts before reactivating the saved attempt. The browser showed the collapsed optional tools and the recovery action after staging restart; provider and task engine tests passed.
5. **The first independent reviewer judged the whole CMS against the PLAN.md-only step.** The reviewer rejected the step even though its own response said the plan was coherent, because API, UI, and viewport evidence were not yet present. `internal/worker/review.go` now receives step title, instructions, and checks, and explicitly judges only that step. `internal/taskcoord/service.go` passes the step contract. A regression test covers this scope. The Task UI now offers a new attempt after `post_review_rejected` without mutating the approved plan.
6. **Mouse activation of Plans overview controls was inconsistent in the test browser.** The visible buttons did not navigate through the automation click path, while keyboard Enter on the same button opened the Task. The Task view is reachable; this needs a normal pointer test before assigning a product defect.
7. **Approved post-test review could not close a step after a restart.** Recovery increased the step lifecycle revision, so earlier frozen checks became stale even when the proposal files still matched their immutable hashes. The review verdict and attempt completion had been persisted, but step finalization failed with `step check rg --files has no passing validation`. The coordinator now carries the original check evidence into the current lifecycle revision with an explicit audit trail only after verifying proposal source hashes and the saved bundle; it can finish an existing approved decision without calling the reviewer again. A paused run with an approved, completed attempt has a distinct recovery action. This was exercised in the isolated browser and step 1 completed without another model request.
8. **A failed provider proposal left a running attempt that the UI offered to replay.** The server correctly refused the duplicate observed effect, but the form still invited another click. A recovery action now requires a saved `provider.propose` failure receipt and no unresolved effects, then atomically marks the attempt, run, and step failed while retaining the approved plan. The browser showed the fresh model/file picker afterward; the failed call was not replayed.
9. **Fixed worker output reservation silently truncated multi-file changes.** The original `worker` preset reserved only 1,500 tokens even with a larger model. Immutable medium/large/max worker presets now select the largest contract the chosen provider can support before the attempt binds. An incomplete structured call ending at the output limit reports a specific truncation reason. The API bundle still exceeded 8,192 tokens, so the approved plan was revised into smaller file steps rather than accepting partial output.
10. **Planning a ten-step correction also exceeded the original 5,120-token planner cap.** A rejected plan can use an immutable 8,192-token planner preset when the model supports it. Plan revision 4 has ten dependent file steps and was inspected and approved in the staging browser. The previous model proposal that exposed drafts on the public page was rejected with explicit feedback.
11. **Rejecting a source proposal had no direct retry path.** Added a transition that closes only a rejected, unapplied proposal with no unresolved effects and preserves its review rationale. The next attempt includes that step's saved human feedback while retaining the approved plan. The staging browser exercised this path after an API proposal used the wrong data path, field names, and route shape.
12. **Some model proposals omitted both allowed edit representations.** A single-file index proposal failed `each change requires exactly one of content or edits`; its effect was recorded and closed without a write. The bounded worker prompt now explicitly requires `content` or a nonempty `edits` array on every changed path. This is a prompt improvement, not proof that the model will comply; the revised attempt remains under review.
13. **A syntactically valid index proposal did not use the CMS API.** Qwen produced hardcoded articles and inserted article fields via `innerHTML`. The user-review gate rejected it before application and saved exact feedback to fetch `/api/articles`, filter `published`, use `textContent`, and encode article IDs in links.
14. **Article and admin proposals repeatedly departed from the approved architecture.** The first article page embedded fake articles and `innerHTML`, so it was rejected; a compact article skeleton with `data-filter=published` passed. The first admin page implemented a separate localStorage CMS, disconnected from the tested API; it was rejected. A later admin page duplicated a large CSS block despite a separate stylesheet step, so it was also rejected. Saved user feedback currently includes only the most recent rejection for a step; later feedback must restate earlier requirements to avoid regression.
15. **CSS proposals from Bonsai were structurally invalid.** Both a four-file context attempt and a single-file CSS attempt failed the source-change validator (`each change requires exactly one of content or edits`) with observed failure receipts. Neither wrote files. The UI recovered both; Qwen then proposed only `public/style.css`, whose breakpoints and selectors were reviewed, applied, checked, and independently approved (7/10 steps).
16. **Client proposal used the wrong API despite passing JSON validation.** Qwen's first `app.js` read and wrote `/data/articles.json`, which `server.js` does not expose as a writable API; it also inserted article content via `innerHTML` and accessed page-specific DOM nodes without guards. Human review rejected it before apply. The next attempt is bound to the actual server file, three pages, seed schema, and explicit endpoint/DOM/security feedback.
17. **Repeated proposal corrections lost older feedback.** The original coordinator supplied only the newest rejection rationale, so a later admin correction sometimes reintroduced an earlier rejected behavior. `LatestRejectedProposalFeedback` now includes up to three recent reviews for the same task step in chronological order; a focused regression test covers preservation and ordering. This code is in staging version 13, with the new client attempt exercising it.
18. **The corrected client exceeded Qwen's configured output reserve.** A six-file context request failed before generating; a four-file request produced an incomplete tool response at the 3,072-token output limit. Raising the profile to 4,096 still truncated the tool response. Both failure effects were observed and closed before retry. The isolated Qwen server and staging provider profile now use 16,384 context and 8,192 maximum output tokens; a bounded five-file proposal is in progress. This is a test configuration change, not evidence that the client works.
19. **Mobile visual inspection found an unreadable header link and an exposed article ID field.** At 390px the admin form stayed within the viewport, but the header link was blue on a blue bar because the CSS targets `.site-nav a` while the markup uses `a.site-nav`. The edit form presents an ID input although the server generates IDs. These are open UX defects and require a post-JavaScript correction plus browser verification.

## Scope of this evidence

The local models and staging server are test infrastructure. Their availability and output speed are not proof that the CMS app works. The full journey remains **unverified** until API CRUD, draft isolation, three user pages, responsive behavior, and completion review pass in the browser with saved artifacts.
