# เปรียบเทียบ flow Codex กับ Hermetrix และแผนปรับปรุง

วันที่ 2 ตุลาคม 2026 · สถานะ: ตรวจและทดสอบแล้ว; แผนปรับปรุงยังไม่ได้ลงมือเปลี่ยนโค้ดผลิตภัณฑ์

> ผลในเอกสารนี้เป็นช่วงเปรียบเทียบก่อนลงมือแก้ ต่อมามีการแก้ Harness และสร้าง/ตรวจ Delivery จริงแล้ว ดู [ผลการทดลองล่าสุด](2026-10-02-hermetrix-delivery-supervised-trial.md) โดยยังคงหลักฐานและข้อสรุปของช่วงเดิมไว้

## ข้อสรุป

Hermetrix มีแกนงานที่ใช้ได้จริง: โมเดลในเครื่องตอบได้ เครื่องมือเขียนไฟล์หยุดรออนุมัติ และหลังอนุมัติเขียนไฟล์ตรงตามตัวอย่างพร้อมอ่านกลับมาตรวจ ประวัติคำสั่งและการอนุมัติกลับมาได้หลังโหลดหน้าใหม่ แต่ยังต้องมีคนช่วยตรวจคุณภาพแผนและความหมายของผลทดสอบ จึงยังสรุปไม่ได้ว่าระบบทำงานอัตโนมัติครบทุกงานโดยไม่ต้องช่วย

ข้อดีจาก Codex ที่ควรนำมาใช้คือการรักษาบริบทของงานให้ต่อเนื่อง: เลือกโปรเจกต์ → บอกผลที่ต้องการ → ตรวจแผน → เห็นความคืบหน้า → ตรวจการเปลี่ยนแปลง → ตรวจหลักฐานและให้คำตอบต่อ ใน Hermetrix ควรเชื่อมขั้นเหล่านี้กับงานเดียวกันให้ชัด โดยรักษาการอนุมัติเฉพาะการเปลี่ยนแปลงและหลักฐานตามฉบับเดิมไว้

## ขอบเขตและที่มาของการเปรียบเทียบ

- Hermetrix: ใช้แอปที่รันจริง `http://127.0.0.1:18801/` กับ Bonsai ที่ `127.0.0.1:8088` ผ่านหน้าเว็บจริง สร้างโปรเจกต์ทดสอบและไฟล์ใต้ `.tmp-ui/codex-flow-audit-project` แยกจาก Easiiot
- Codex: อ่านข้อมูลปัจจุบันจาก OpenAI Docs และตรวจข้อมูลการจัดโปรเจกต์/แชทในแอปผ่านเครื่องมืออ่านสถานะ ไม่ได้ควบคุมหรือทดสอบหน้าจอ Codex desktop แบบ A/B และไม่ได้อ้างว่าเป็นผลทดสอบ Codex ทุกฟีเจอร์
- ชุด Chrome ที่มีอยู่ใช้บริการ Hermetrix จริงและโมเดลจำลองสำหรับผลที่ควบคุมได้ แยกจากการลอง Bonsai จริงในแอปปัจจุบันด้านล่าง
- งานนี้เป็นการเปรียบเทียบ วางแผน และตรวจ flow ไม่ได้เปลี่ยนโค้ดแอปหรือคลายสิทธิ์เดิม

## ความเข้าใจผลิตภัณฑ์

ผู้ใช้คือคนที่ต้องการมอบหมายงานในเครื่องและตรวจผล โดยไม่ต้องเข้าใจโครงสร้างภายในก่อน วัตถุหลักคือโปรเจกต์ งาน แชท แผน การเปลี่ยนแปลง และหลักฐาน หน้าเป็น workbench ที่มีอยู่แล้ว ควรปรับทีละส่วนแทนการเปลี่ยน framework

สิ่งที่ผู้ใช้ควรตัดสินใจครั้งแรกคือ “จะคุยทั่วไปหรือทำงานในโปรเจกต์ไหน” ความสำเร็จคือเริ่มงานในขอบเขตที่ถูก เห็นว่าต้องทำอะไรต่อ ตรวจผลที่เชื่อถือได้ และกลับมาทำต่อได้หลังเปิดใหม่ เมื่อมีข้อผิดพลาดต้องเก็บร่าง เหตุผล และคำตัดสินไว้พร้อมทางแก้ มือถือต้องเข้าถึงสถานะและการตัดสินใจสำคัญก่อนรายละเอียดเครื่องและ token

## จุดที่ใช้งานยากหรือยังไม่ผ่าน

### F01 · P1 — วิธีตรวจจากแผนอาจผ่านทั้งที่ไม่พิสูจน์ผล

โจทย์คือเพิ่ม Status: ready ใน README และเก็บ sum.js เหมือนเดิม ฉบับ 1 ใช้ `git diff -- sum.js` แต่ไฟล์ไม่ได้ถูกติดตามและ Git root เป็น repository แม่ คำสั่งจบ 0 โดยไม่มีข้อมูลที่พิสูจน์ว่าไฟล์เดิมอยู่ครบ

หลังส่ง feedback ฉบับ 2 เปลี่ยนเป็น node แต่เพียงแสดง Hash object ไม่มี digest หรือการเทียบค่าที่คาดหวัง ทดสอบคำสั่งเดียวกันกับไฟล์ถูกและไฟล์ที่เปลี่ยนเป็นลบแทนบวกแล้วได้ exit 0 ทั้งคู่ รายละเอียดอยู่ `.tmp-ui/codex-flow-semantic-probe.json` ทั้งสองแผนไม่ได้รับอนุมัติให้ทำงาน ฉบับ 2 ถูกส่งกลับแก้ ไม่มีการลองสั่งโมเดลวนเพิ่ม

ตัวตรวจปัจจุบัน `internal/taskcoord/plan_checks.go` ตรวจรูปคำสั่ง executable และการมี Git repository แต่ไม่ได้พิสูจน์ความหมายของ assertion; planner รับ manifest ที่ไม่บอกว่าไฟล์ใดถูก Git ติดตาม การผ่านตัวตรวจโครงสร้างจึงไม่เพียงพอ ข้อเสนอคือใช้ check ชนิดที่ระบบสร้างเองสำหรับ file/hash invariants และเก็บ custom checks ไว้โดยไม่เหมารวมว่าเชื่อถือได้ ห้ามทดลองรัน custom command ที่ยังไม่อนุมัติบน source จริงเพื่อ preflight

### F02 · P1 — Run อาจบันทึกไฟล์ที่ผู้ใช้ยังไม่ได้ตั้งใจแก้

เปิด sum.js ที่เป็น CRLF 38 bytes แล้วกด Run โดยไม่แก้ข้อความ ก่อนเปิด UI ขึ้น Saved หลัง Run ไฟล์กลายเป็น LF 37 bytes SHA256 เปลี่ยนจาก `472087cd…` เป็น `99140f58…` หลักฐานก่อน/หลังอยู่ runtime receipt และสำเนา `.tmp-ui/codex-flow-sum-after-run.js`

เส้นทาง Run เรียก captureCodeDraft และบันทึกเมื่อ content ต่างจาก originalContent; editor ใช้ document string ซึ่ง normalize line endings การระบุ dirty กับ serialization ต้องตรวจและแก้ร่วมกัน ไม่ควรข้าม SHA preimage gate หลังเก็บหลักฐานได้คืนเฉพาะ sum.js ใน fixture เป็น bytes เดิมและตรวจ hash ตรง baseline แล้ว ไม่มีการเปลี่ยนไฟล์ Easiiot

### F03 · P2 — Test ที่ไม่มี tests ขาดสรุปเตือน

ปุ่ม Test ของ JavaScript เลือก `node --test` โดยตรง ผลแสดง completed และ Exit 0 ทั้งที่ TAP บอก tests 0 ไม่มีข้อความหลัก “ยังไม่มีชุดทดสอบ” ผู้ใช้ต้องตีความ output เอง ต้องแยก command completed, tests executed และ outcome verified ออกจากกัน โดยไม่เปลี่ยน exit code ที่จริง

### F04 · P2 — บริบทแชท/โปรเจกต์/ตรวจงานสลับกันไม่ชัด

เริ่มคุยที่หัวแอปมีโปรเจกต์สร้าง personal session ตามการออกแบบเดิม ระหว่างมี personal session ค้างอยู่ Workspace ตรวจงานแสดงแชทส่วนตัวและ jobs เดิมจากโปรเจกต์อื่น ขณะที่ช่องไฟล์เป็นโปรเจกต์ทดสอบ ปุ่ม Agent จาก Editor เรียก switchView(chat) จึงกลับไป session นั้นได้ หลัง coding assistant สร้าง project session แล้ว main Chat จึงแสดง project session ได้ถูกต้อง

ไม่พบหลักฐานว่ามีการเขียนข้ามขอบเขต แต่ข้อมูลบนหน้าจอทำให้เข้าใจว่าเป็นงานเดียวกันได้ ควรแสดง owner ของแต่ละส่วนและใช้ “แชทของงานนี้” เป็นทางเข้าที่ชัด โดยรักษา personal session ที่ไม่มี tools ตามเดิม

### F07 · P3 — รายละเอียดที่เพิ่มภาระในการอ่าน

## แผนปรับปรุงตามลำดับ

### ระยะ 1 — ทำให้ผลและการเปลี่ยนไฟล์เชื่อถือได้

1. แก้ F02 ให้ open → Run/Test ที่ไม่ได้แก้ข้อความคง bytes/hash เดิม ทั้ง CRLF/LF/BOM ที่รองรับ และ UI dirty state ตรงกับสิ่งที่จะบันทึก แก้บั๊กนี้โดยไม่ถอด preimage guard
2. แก้ F01 ด้วย typed checks สำหรับ invariant ที่ระบบพิสูจน์ได้เอง: contains/exact-content/hash พร้อมตัวตรวจถูกและผิด; planner อ้างอิง snapshot/hash ที่ capture จริง แสดง custom command เป็นวิธีตรวจที่ต้อง review และไม่ยกระดับคำกล่าวของโมเดลเป็นหลักฐาน
3. แก้ F03 โดยแสดง “คำสั่งทำงานสำเร็จ แต่ยังไม่มีการทดสอบ” เมื่อมีข้อมูลพิสูจน์ tests 0; runner ที่ parse ไม่ได้แสดง unknown ไม่เดาว่าผ่าน และเกณฑ์ mandatory test ต้องไม่ครบเพียงเพราะ process exit 0

ไฟล์ที่เกี่ยวข้อง: `internal/web/ui/ide-workspace.js`, `internal/web/ui/app.js`, `internal/web/vendor-src/ide-entry.js`, `internal/taskcoord/plan_checks.go`, planner/worker และการผูก evidence ใน taskengine ตรวจผลหลักด้วย fixture นี้และโครงการจริงที่มี tests; เพิ่มเฉพาะ regression ที่จับข้อผิดพลาดด้านพฤติกรรม

### ระยะ 2 — ทำให้เห็นงานเดียวและการตัดสินใจถัดไป

1. ขอบเขตงานก่อนส่ง: แชทส่วนตัว / โปรเจกต์ / งานที่ผูกอยู่ แสดงเป็นข้อความสั้นที่ติดกับ composer
2. ทางเข้างานเดียวมีสรุปเป้าหมาย สถานะ แผน และปุ่มถัดไปหนึ่งปุ่มที่ตรงกับ current revision ช่องแชท diff และหลักฐานติดป้ายว่าเป็นของงานไหน
3. หน้ารวมแยก “ทุกโปรเจกต์” และ “โปรเจกต์นี้”; แผนถูกส่งกลับอยู่กลุ่มรอคุณจัดการ และปุ่ม “แก้แผน” ไม่แนะนำให้ทำขั้นเขียนไฟล์
4. แสดงความต่างของแผนเป็น field/check/effect scope ที่เปลี่ยนจริง สรุปสิ่งที่แก้ไฟล์และ feedback ผูกกับ revision/hash

Acceptance: สร้างงานใน A เปิด personal chat และเปลี่ยนไป B แล้วกลับมา สถานะ ข้อความ ปุ่มและการอนุมัติต้องยังเป็นของ scope ที่ถูก ไม่มีผลเก่าถูกใช้ปิดงานใหม่ หน้ารวมไม่สื่อว่ากำลังรันเมื่อรอผู้ใช้

### ระยะ 3 — ควบคุมงานที่ใช้เวลาโดยไม่สูญเสียความคืบหน้า

1. ให้ร่างคำสั่งต่อได้ระหว่างทำงาน และมี Queue แบบเห็นรายการ/ยกเลิกได้ แต่ยังใช้ turn lease และตรวจ scope เมื่อถึงคิว
2. Stop ผูก turn/run โดยมี receipt บอกว่าหยุดตรงไหนและผลใดเกิดไปแล้ว; หากไม่ทราบผลต้อง reconcile ก่อนทำต่อ
3. เพิ่ม Steer ภายหลัง: เปลี่ยน requirement เป็นฉบับใหม่และ invalidate สิ่งที่เกี่ยวข้อง ไม่ฉีดคำสั่งเข้าแผนที่มีอำนาจเดิมโดยเงียบ ๆ
4. แถบงานกำลังทำ รอคุณตัดสินใจ หยุดแล้ว และผลพร้อมตรวจ มาจากสถานะจริง ไม่ใช้ spinner หรือ token meter แทนผลสำเร็จ

Acceptance: หยุดก่อน dispatch, ระหว่างคำสั่ง และหลัง effect แล้วเปิดใหม่ ไม่มี effect replay และไม่มีข้อความรออนุมัติค้างทั้งที่ทำแล้ว Queue ต้องไม่ส่งเข้าโปรเจกต์ที่ผู้ใช้เปลี่ยนไปโดยผิด scope

### ระยะ 4 — ลดภาระการหาปุ่มและกลับมาทำต่อ

เพิ่มค้นหาแผน/งาน/แชทภาษาไทยใน palette ตั้ง accessible label ให้ช่องค้นหา กู้แท็บไฟล์หลังเปิดใหม่โดยตรวจไฟล์ที่เปลี่ยนจากภายนอก ย่อข้อมูลเครื่อง/token และ toolbar เมื่อหน้าต่างเตี้ย ใช้แผงย่อยแทนการเพิ่มช่องจนต้องเลื่อนหา CTA แปลสถานะหลักให้เป็นภาษาเดียวกันและคงรายละเอียดเทคนิคไว้ให้เปิดดู

Acceptance: ทดสอบ desktop 1280×720 และ 1440×960, tablet 768×900, mobile 390×844 พร้อมคีย์บอร์ด ร่างและไฟล์ที่แก้ยังไม่บันทึกไม่หาย ปุ่มตัดสินใจมองเห็น/เข้าถึงได้ ข้อความยาวไม่ดันหน้าออก และ reduced motion ยังคง feedback ที่อ่านได้
